# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Documentation maintenance

After every change, check whether `AGENTS.md` (root, `backend/`, `frontend/`) and `README.md` (root, `frontend/`) need updating. Keep these files in sync with the actual code — new modules, routes, DB keys, API endpoints, and dependency versions must be reflected here.

## Commands

- `bun dev` — Start dev server (Vite, port 5173)
- `bun run build` — Type-check with `tsc -b` then Vite production build
- `bun run lint` — Oxlint with type-aware rules (`oxlint --type-aware`, config in `.oxlintrc.json`); TypeScript 7 (native `tsc`) means typescript-eslint is not used
- `bun run test` — Run the tests once (`vitest run`); `bunx vitest` watches, `bunx vitest run <file> -t <name>` narrows
- `bun run preview` — Preview production build locally
- `npx shadcn@latest add <component>` — Add a shadcn/ui component (e.g. button, table, dialog)

## Architecture

React 19 + TypeScript 7 SPA built with Vite 8. No SSR — this is a CRUD/business app behind auth.

**Modules:** Each feature module lives in `src/modules/{id}/` (routes, components, hooks, lib/repository, config, types.ts) and exports a `ModuleDefinition` (`src/types/modules.ts`): id, basePath, i18n label key, icon, route objects, a `SidebarSection`, and an optional `HomeCard`. `src/modules/registry.ts` lists all modules in order; the router, sidebar, and homepage are driven by it. Users enable/disable modules in settings — `useModules()` (`src/hooks/use-modules.ts`) derives enablement from the shared `["settings"]` query, the sidebar and homepage only mount enabled modules, and every module route has a `beforeLoad` guard (`src/modules/guard.ts`) that redirects to `/` when the module is disabled.

**Routing:** TanStack Router with type-safe route definitions. The router is created in `src/routes/router.ts` from core routes (homepage, login, settings) plus each module's routes; root layout in `src/routes/__root.tsx`. Route objects are defined next to their page components in `src/modules/{id}/routes/` and collected in that module's `routes/routes.ts`. All routes use `rootRoute` as parent with full paths (flat structure, no nested layout routes).

**Data fetching:** TanStack Query. The shared `QueryClient` lives in `src/lib/query-client.ts` (used by both `App.tsx` and route guards). Hooks live with their module (`src/modules/{id}/hooks/`); shared hooks (auth, settings, categories, modules) in `src/hooks/`.

**Capabilities:** `useCapabilities()` (`src/hooks/use-capabilities.ts`) reads server-wide feature flags from `GET /api/v1/capabilities` (`staleTime: Infinity`, they only change with a server restart). The capabilities are `{llm, llmVision, bankImport}` (`llmVision`: a vision model is configured, quick add accepts photos); the bank import UI (sidebar link, dashboard card, consent banner, routes) is hidden while `bankImport` is false (the default until the query resolves). LLM-backed UI must hide its actions while `llm` is false (the default until the query resolves). The ledger email screens are the exception that shows a notice instead: `LedgerEmailLlmNotice` explains that scanning needs the LLM, the scan and upload buttons are disabled and the account dialog hides the pre-classification switch. A folder scan is a background job: `LedgerEmailAccountCard` starts it with `useStartLedgerEmailScan` (202) and `useLedgerEmailScanStatus(id, onFinished)` polls `GET /ledger/email-accounts/{id}/scan` (key `["ledger","email-scan",id]`) every 2 s while `state` is `running`, shows the progress, and on the change from running to finished invalidates accounts, orders and transactions and toasts the result; since the status is fetched on mount, a reload (or a scheduled scan) is picked up the same way. `.eml` uploads stay one request (`useUploadLedgerEmailMessages`) and report from the response. The account dialog (`LedgerEmailAccountDialog`) keeps the folder as a free-text input and adds "Load folders": `useLedgerEmailFolders` posts the connection as entered (the password only when typed, plus the account ID when editing, so the backend can use the stored one) to `POST /ledger/email-accounts/folders`, and `LedgerEmailFolderList` shows the result as a list filtered by what is typed (`visibleFolders` in `lib/email-folders.ts`; all folders while the field is empty or holds a listed name); clicking one fills the input. A failed listing shows a translated message by error code (`ledger.email.foldersErrors.*`) and the input stays usable.

**Draft inbox:** `/inbox` (`src/routes/inbox.tsx`, components in `src/components/drafts/`, `useInboxAvailable`/`usePendingDrafts` in `src/hooks/use-drafts.ts`) lists pending drafts. It and its sidebar entry (with pending-count badge) exist when `useInboxAvailable()` is true: `llm` and paperless configured, **or** `GET /drafts/summary` (`draftSummaryQueryOptions`, key `["drafts","summary"]`, refetched every 60 s and invalidated with every `["drafts"]` change) reports at least one draft (e.g. created by an agent through MCP). The route's `beforeLoad` redirects to `/` only when neither holds; it fetches the summary fresh (`staleTime: 0`) so a draft that just arrived opens the page, and keeps swallowing non-redirect errors. Draft types are the eight entity types (`draftEntityTypes` in `draft-input.ts`: purchase, contract, cost, vehicle, contract/purchase/ledger category, ledger account) plus `none`; `ClassifiedEntityType` (purchase, contract, cost) is what the classifier and quick add know. `parentKind`/`parentRequired` say what a draft's parent is (category, vehicle, optional ledger parent category, or none) and `targetProblem` skips the parent checks for types without a required parent. Type and target pickers only offer enabled modules; the parent select appears only for types with parent options and offers "no parent" for ledger categories. Accept opens the module's create dialog with `initialValues` (`PurchaseDialog`, `ContractDialog`, `CostEntryDialog`, `VehicleDialog`, `CategoryDialog` for both category kinds, `LedgerCategoryDialog`, `LedgerAccountDialog`; pass a memoized object), creates the entity through the module hook (`PrefilledCreateDialogs`: the dialog's `onSubmit` returns the promise of `onCreate`, which rejects when the create fails, so the dialog stays open with the input, and resolves once the entity exists, which closes it; the two ledger dialogs do not close themselves, so it closes them after success), then calls the accept endpoint (a failed accept is toasted and does not keep the dialog open, the entity exists) (`entityUrl` is always an absolute URL, e.g. `/auto/vehicles/{id}` for a vehicle) and shows returned warnings as toasts. A draft of a disabled module keeps showing with Accept disabled. **Bulk accept:** every card has a checkbox, enabled by the rule that enables Accept (`targetProblem(...) === null`); `BulkAcceptBar` (`bulk-accept-bar.tsx`) above the list has "Select all (n)" for the shown selectable drafts, a type filter (only with more than one type present; changing it clears the selection, and a filter whose last draft is gone falls back to all types) and "Accept selected", which asks once (`AlertDialog`) and then calls `useAcceptDraftsBatch` → `acceptDraftsBatch` (`POST /drafts/accept-batch` with `baseUrl = window.location.origin`, `draftBatchChunkSize` 25 ids per request, sequential, with progress; it never throws and returns `{results, error?}` so results before a failed request are kept). The backend creates the entities, so no create dialog and no module mutation is involved and the hook invalidates all queries afterwards. Accepted drafts leave the selection; failed and unprocessed ones stay selected. A failed draft shows its reason on the card (`drafts.bulk.errors.<code>`, `invalid_input`/`conflict` with the backend's message) until it is edited or decided; the reasons live in page state, not on the draft. Strings under `drafts.bulk.*`. Draft `note` codes are translated via `drafts.notes.*`; the free-text note of an MCP draft (`source.kind === "mcp"`) is shown as is. Sources are `paperless` (thumbnail and "Open in paperless" link, only for this kind), `ledger` (recurring-payment contract drafts with notes `recurring_payment`/`recurring_payment_ended`; the user picks the category, the card shows interval and end date) and `mcp`. `useAcceptDraft` also invalidates `["ledger"]` and `["contracts"]`, since accepting a ledger draft links its payments to the new contract. The paperless settings card shows the pipeline section (switch, tag names, Run now) only when `llm` is true. "Test connection" shows its result inline below the buttons as well as in a toast; the result is cleared when the URL or token is edited, saved or removed.

**Access tokens:** the settings page ends with `TokensSettingsCard` (`src/components/tokens/`, `useTokens`/`useCreateToken`/`useRevokeToken` in `src/hooks/use-tokens.ts`, `src/lib/token-repository.ts`, `src/types/token.ts`, strings under `tokens.*`). It lists the user's personal access tokens (name, scope badges, created, expiry or "never" with an `Expired` badge, last used), creates them in `TokenCreateDialog` (name, scope checkboxes for `tokenScopes` (`read`, `drafts`, `links`, `categorize`; sent in that order) with `read` preselected and at least one required, expiry 30/90/365 days, custom date or never; default 90, "never" shows a warning; `expiresAt` is computed by `expiryFor` in `token-expiry.ts`, sent as an ISO timestamp and omitted for never) and revokes them through `DeleteConfirmDialog` (`actionLabel`). The raw token comes only in the create response: it is shown once in `TokenRevealDialog`, kept in component state, cleared on close and never written to the `["tokens"]` query cache (the mutation is reset right after, and `useCreateToken` has `gcTime: 0` so the response also leaves the mutation cache at once). Below the list the card shows the MCP URL (`window.location.origin + "/mcp"`), copyable Claude Code and OpenCode snippets with a `<your-token>` placeholder, the scope explanation and the security notes (tokens also work against the REST API, `read` includes the export, revoke leaked tokens).

**Email drafts:** the ledger email account dialog has an optional "Folder for the Kontor inbox" (`draftsFolder`, only with the `llm` capability; the zod schema refuses the order folder, the loaded folder list is reused through `LedgerEmailFolderList`'s `label` prop). `LedgerEmailAccountsPanel` shows "Check Kontor inbox folders" when an account has such a folder (`useRunLedgerEmailDrafts`, `POST /ledger/email-drafts/run`, one run for all accounts; toasts with the counts and the server's warnings, invalidates `["drafts"]`). `email` drafts use the generic draft card; accepting one toasts `drafts.acceptedEmail` (`acceptedKeys` in `inbox.tsx`). `EmailSourceSection` (`src/components/email-source-section.tsx`, `useLedgerEmailLinks`, key `["ledger","email-links",entityType,entityId]`) shows the email an entity was created from (subject as a `mid:` link when the Message-ID is known, sender, date, account) on the contract and purchase detail routes and, inline, in the documents dialog of a cost entry (that dialog is only reachable with paperless configured); it renders nothing while the ledger module is disabled or the entity has no source email.

**Processed emails:** the account dialog renders `LedgerEmailProcessedAction` (`ledger-email-processed-action.tsx`: a radio group keep/move/delete, for move a target input with the loaded folder list) for the order folder and, with the `llm` capability and a non-empty `draftsFolder`, for the Kontor inbox folder (`processedAction`/`processedFolder`, `draftsProcessedAction`/`draftsProcessedFolder`; strings under `ledger.email.processed.*`). The zod schema requires a move target and refuses either scanned folder; on submit the target is cleared unless the action is `move` and the drafts action is reset to `keep` without a drafts folder. When an action changes to `delete` the dialog asks first (`DeleteConfirmDialog`) and only then calls `onSubmit`. `LedgerEmailAccountCard` shows a configured move or delete (`processedSummary`).

**Quick add:** `QuickAdd` (`src/components/quick-add/quick-add.tsx`) sits in the root layout header: button plus Ctrl/Cmd+K, rendered only when `useQuickAddTypes()` (`src/hooks/use-quick-add.ts`; `llm` capability and enabled purchases/contracts/auto) is non-empty. `QuickAddDialog` posts the note to `/api/v1/quick-add`; a `confident` proposal whose type and category/vehicle pass `targetProblem` goes straight to `PrefilledCreateDialogs`, otherwise it shows `TargetPicker` with the translated note (`quickAdd.notes.*`) or currency hint; picking another type re-runs the request with `targetType`. After creating, a toast offers "Open" (`entityPath`). The dialog also takes one file ("Attach PDF or photo"; PDF only without the `llmVision` capability; a separate "Take photo" button with `capture="environment"` on touch devices, because a mixed `accept` does not reliably offer the camera on Android). `prepareQuickAddFile` (`src/lib/quick-add-file.ts`) checks the 10 MiB limit and scales images down to a JPEG of at most 2000 px (`createImageBitmap` with EXIF orientation; an image the browser cannot decode, e.g. HEIC outside Safari, is `unsupported_file`). With a file the request is multipart (`postForm`) and the text is an optional hint; picking another type re-sends the file. Error codes of the endpoint and of the file check are translated via `quickAdd.errors.*`. The typed text and the file are kept until an entry is created. Shared with the inbox (`src/components/drafts/`): `TargetPicker`, `useParentOptions`, `PrefilledCreateDialogs`, and `draft-input.ts` (`initialValues`, `targetProblem`, `entityPath`/`entityUrl`, `PrefillEntry`).

**Forms:** React Hook Form + Zod for validation via `@hookform/resolvers`. Field configs in `src/modules/{id}/config/` drive both form and table rendering via `FormFieldRenderer`. Entity dialogs (`ContractDialog`, `PurchaseDialog`, `VehicleDialog`, `CostEntryDialog`, `CategoryDialog`) take `onSubmit: (data) => Promise<unknown>` (callers pass `mutateAsync`) and close through `useDialogSubmit` (`src/hooks/use-dialog-submit.ts`) only once it resolves; on a rejection they stay open with the input, Save is disabled while it runs, and the error comes from the global mutation toast.

**Styling:** Tailwind CSS v4 with the Vite plugin. shadcn/ui for pre-built components (config in `components.json`, components go in `src/components/ui/`). Use the `cn()` helper from `@/lib/utils` for conditional classNames. Toasts (sonner, `src/components/ui/sonner.tsx`, mounted once in `App.tsx`) use `richColors`, so success, error, warning and info toasts are coloured.

**Charts:** Recharts, used by the auto module's vehicle statistics page (`/auto/vehicles/$vehicleId/statistics`) and the ledger analysis page (`/ledger/analysis`), both lazy-loaded. Cost-type series colors are CSS custom properties (`--viz-*`) defined for light and dark mode in `src/index.css` and mapped in `src/modules/auto/config/chart.ts`. The tooltip box and the legend (`ChartTooltipBox`, `ChartLegend`, `src/components/charts/chart-parts.tsx`) and the axis styles (`AXIS_TICK`, `AXIS_LINE`, `chart-axis.ts`) are shared by the modules; neither file imports Recharts. **Ledger charts:** `modules/ledger/components/ledger-analysis-charts.tsx` is the only file of the ledger module that may import `recharts`; helpers, sections, legends and the dashboard stay Recharts-free, so only the analysis route's chunk pulls the library in. Legends are plain HTML below the chart (`ChartLegend`), not a Recharts `<Legend>`, so they render without the SVG. Category series use the palette `--viz-cat-1..10` plus `--viz-cat-other` and `--viz-cat-uncategorized` (light and dark in `src/index.css`, no hex values in components): a category's preferred color is its position among its siblings by `createdAt`, then `id`, modulo 10 (`siblingColorIndex` in `lib/analysis-series.ts`), which depends only on the category tree, so it is the same for every range (deleting a category shifts the siblings created after it). The series drawn in one chart always have different colors (`distinctPaletteIndexes`): with more than ten siblings two can prefer the same color. The assignment has two passes over the drawn order (largest total first): first every series whose preferred color is still free takes it, so the largest of a colliding group and every series that collides with none keep their preferred color; then each of the others takes the next free color above its preferred one, which is a color no drawn series prefers. So a color can only differ between ranges for a category whose index collides with a larger drawn one; a collision never moves a third category. At most 9 category series are drawn (`maxCategorySeries`) from ten colors, so a free one always exists; the rest is summed into "Other"; "Uncategorized" and the amounts booked directly on a parent use the neutral color. The cash-flow series use `--viz-income`, `--viz-expenses` and `--viz-net`. Every light value of these has at least 3:1 contrast against the white card and the category colors keep a minimum distance from each other (`lib/palette.test.ts` reads `src/index.css`; change a value and the test tells). The shared legend and tooltip key their entries by position, because names from user data are not unique (`src/components/charts/chart-parts.test.tsx`).

**Path alias:** `@/` maps to `src/` (configured in both tsconfig and vite.config).

**i18n:** `react-i18next` with locale files in `src/i18n/locales/` (en.json, de.json).

**Import/export:** The settings page offers full export/import plus per-module export/import against `/api/v1/export`, `/api/v1/import`, and `/api/v1/modules/{id}/export|import` (v2 envelope format). Exports are plain downloads; the restore and the module import are mutations (`useRestoreBackup`, `useImportModule` in `src/hooks/use-settings.ts`, `restoreBackup`/`importModuleData` in `src/lib/settings-repository.ts` parse the file in the browser) that invalidate every query on success, so settings and module data refresh without a reload; errors (also a file that is no JSON) come from the global mutation toast. The backend imports only into modules without entries but replaces their categories (and, for the full restore, the settings), so the full restore always asks first (`DeleteConfirmDialog` with the file name, `settings.restoreConfirm`) and the module import asks for the modules with categories (`importReplacesCategories` in `routes/settings.tsx`: contracts, purchases, ledger; auto imports at once).

Ledger review queue (`/ledger/review`, `ledger.review.tsx`, `ledger-review-list.tsx`, `ledger-review-panel.tsx`, logic in `lib/review-queue.ts`; strings under `ledger.queue.*`): `useLedgerReviewQueueAll` loads the whole queue in one request (`GET /ledger/transactions?limit=all`, key `["ledger","review",{limit:"all"}]`); the dashboard and home card keep `useLedgerReviewQueue(10)`.
