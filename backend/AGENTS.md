# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Documentation maintenance

After every change, check whether `AGENTS.md` (root, `backend/`, `frontend/`) and `README.md` (root, `frontend/`) need updating. Keep these files in sync with the actual code — new modules, routes, DB keys, API endpoints, and dependency versions must be reflected here.

## Prerequisites

- **Go 1.27+** — https://go.dev/dl/
- **Task** — Task runner (taskfile.dev): `go install github.com/go-task/task/v3/cmd/task@latest` or `pacman -S go-task`
- **Air** — Live reload for Go: `go install github.com/air-verse/air@latest`
- **golangci-lint** (optional) — Linter: `go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0` or `pacman -S golangci-lint`; use the version CI pins in the root `.tool-versions` (`task lint` warns on a mismatch)

- `task lint` — Run golangci-lint (warns if the installed version differs from `.tool-versions`)

## Architecture

Go 1.27+ stdlib `net/http` with method+pattern routing. Single binary that optionally serves the frontend SPA.

**Modules:** Each feature module implements the `module.Module` interface (`internal/module`): `ID`, `Prefix` (its DB key prefix), `Migrations`, `RegisterRoutes`, `Seed`, `StartBackground(ctx, wg)` (background services end with `ctx` and run on the app's shared `*sync.WaitGroup`, see **Shutdown**), `IsEmpty`, `ExportSection`, `ImportSection`, `PruneDeadLinks`. The server builds all modules, registers them in a `module.Registry` (order matters — it is also the import order), runs their migrations, and registers their routes through `module.Router`, which wraps every handler in the enablement gate. Users can disable modules in settings (`disabledModules`, stored as the disabled set so everything defaults to enabled); gated routes return `403 {"code":"module_disabled"}`. Data of disabled modules is kept.

**Cross-module links:** Ledger transactions reference contract/purchase/vehicle/cost items (`link.RefContract|RefPurchase|RefVehicle|RefCost`), and those items track linked transaction IDs (`linkedTransactionIds`). The synchronization goes through `internal/storage/link.Registry` inside a single badger transaction: the items live on the generic item store `internal/storage/item` (`item.Store[T]`, one per kind: contracts, purchases, vehicles, cost entries; `item.Spec` gives module, key segment, optional parent index, reference type and accessors), which is the `link.Target` of its reference type (AddLink/RemoveLink/Exists); the module stores are thin wrappers with their own method names. The ledger store implements `link.TransactionSide`. The item store owns both link rules, so no module can get them wrong: every delete strips the references to the deleted item from its transactions (`Delete`/`DeleteTxn`, and `DeleteByParentTxn` for the cascades: a vehicle's cost entries, a contract or purchase category's items), and `Update` copies `linkedTransactionIds` from the stored entity inside the transaction, so a link added meanwhile is not lost; links only change through the registry. Keys are unchanged (`{kind}/{id}`, `idx/{index}/{parentId}/{id}` under the module prefix) and pinned by `TestStoreKeys_Pinned` in each module. Modules never import each other; wiring happens in `internal/server`.

**Item inputs:** `ContractInput`, `PurchaseInput`, `VehicleInput`, `CostEntryInput` and `categories.CategoryInput` check themselves in `Validate()` with the shared checks of `internal/validate`: the name (`itemName` for purchases) is trimmed in place and required, dates are `YYYY-MM-DD` (required: `startDate`, cost `date`), amounts, mileages and the maintenance factor are not negative, months are 0..1200, text is capped at 200 characters (names, short fields), 2048 (URLs) and 10000 (comments, consumables, cost description). Every create and update path runs it: the REST handlers (`httputil.Decode[T]`), the MCP draft tools, the draft batch accept and `POST /contracts/import` (per row); importing an export file (`ImportSection`) does not, so old exports keep importing. The entity's `Apply(input, now)` sets the fields an input controls; the create constructors (`newContract`, …, `categories.New`) and the update handlers use it.

**Storage:** BadgerDB (embedded LSM-tree KV store) behind `storage.Engine` (`internal/storage`), shared by per-module stores. Data is stored as JSON documents; every module's data lives under `u/{userId}/mod/{moduleId}/...` (see the root `AGENTS.md` for the full key schema). Sentinel errors (`ErrNotFound`, `ErrConflict`, ledger-specific ones) live in `internal/storage`. JSON helpers (`json.go`): `Get[T]` (a missing key is `ErrNotFound`), `List[T]` (every value under a prefix in key order, never nil), `GetJSON`/`SetJSON` and `IteratePrefix` (with the key); `RetryConflicts` (`retry.go`) reruns a transaction on `badger.ErrConflict` and gives `ErrRetriesExhausted` (an `ErrConflict`, 409) when the attempts run out.

**Migrations:** Per module (`internal/storage/migration`): `migration.RunModule` applies a module's pending migrations against its own `_meta/schema/{moduleId}` version key at startup. A module's migrations must only touch keys under its own prefix.

**Export/import:** Versioned envelope (`{"format":"kontor-export","formatVersion":2,...}`) with one section per module, each stamped with the module's section schema version. Full and per-module endpoints; import requires the affected modules to be empty and enabled, preserves IDs verbatim, strips ledger references to items that were not imported, and prunes dead transaction links (with warnings). Orchestrated in `internal/core/export.go`; each module owns its section shape.

**Backups:** Optional periodic full BadgerDB snapshots (`internal/storage/backup.go`) to `BACKUP_DIR` every `BACKUP_INTERVAL` (default `24h`), keeping the `BACKUP_KEEP` newest files (default 7). Empty `BACKUP_DIR` disables. Restore snapshots with the `badger` CLI (`badger restore`) or `badger.DB.Load`.

**Config:** Environment variables via `caarlos0/env` struct tags. See `.env.example` for all options. `JWT_SECRET` must be at least 32 bytes (`config.MinJWTSecretBytes`, startup error otherwise). `REGISTRATION_ENABLED` is parsed into `config.Registration`: unset = `RegistrationFirstUser`, a `strconv.ParseBool` true = `RegistrationOpen`, false = `RegistrationClosed`, anything else fails at startup.

**Request limits:** `httputil.ReadJSON` reads at most `MaxJSONBytes` (1 MiB) through `http.MaxBytesReader`; `ReadJSONLimit` takes another limit (the export import, `core.MaxImportBytes` = 64 MiB). `httputil.BodyError` answers a failed read with 413 `{"error":"request body too large","code":"body_too_large"}` (`IsTooLarge`, `TooLarge`) or 400 with the handler's text. Multipart handlers call `httputil.LimitBody` before `ParseMultipartForm`, which otherwise only caps memory: contracts import 10 MiB, ledger CSV preview 10 MiB, `.eml` upload 64 MiB (quick add has its own 10 MiB file limit); `/mcp` is wrapped in `middleware.MaxBody` (1 MiB). **Server timeouts** (`newHTTPServer`): `ReadHeaderTimeout` 10 s, `ReadTimeout` 5 min, `IdleTimeout` 2 min, no `WriteTimeout` (the manual bank sync answers after up to 15 min, `/mcp` may stream).

**Shutdown:** `buildModules` creates one `*sync.WaitGroup` (`services.background`, returned as `app.background`). Everything that may still write after a request ended runs on it: backups, the paperless pipeline, every module's schedulers (`StartBackground(ctx, wg)`), the ledger background runs (`SetBackground(ctx, wg)` of `CategorySuggester`, `RecurringService` (both through the shared `userRunner`), `EmailService` for manual scans and `emailActions.Kick`; they start nothing once `ctx` ended) and the welcome mail (`core.Handler.SetBackground`). `Server.serve` stops on SIGINT/SIGTERM with `srv.Shutdown` (10 s) or on a serve error, then cancels the background context and waits up to 15 s (`waitTimeout`, a warning when it runs out). `cmd/server` returns from `run()` before `os.Exit`, so `engine.Close` runs on every path.

**Bank import config:** `ENABLE_BANKING_APP_ID` and `ENABLE_BANKING_KEY_PATH` (RSA private key, PEM, PKCS#1 or PKCS#8) enable the Enable Banking import; `ENABLE_BANKING_API_URL` (default `https://api.enablebanking.com`, for tests and sandboxes) and `ENABLE_BANKING_SYNC_INTERVAL` (default `24h`; `0` disables only the automatic sync, the scheduler still sends expiry mails and prunes states). Startup fails when only one of id/key is set, when enabled without a valid `ENCRYPTION_KEY`, for an invalid URL or negative interval, and in `buildApp` when the key file is unreadable or not RSA. Without id and key the feature is off (info log `bank import disabled`). Enabled without `PUBLIC_URL` logs a warning and consent requests answer 409 `public_url_not_configured`. The key, JWTs and session IDs are never logged.

**LLM:** Optional server-wide OpenAI-compatible endpoint (`internal/llm`). `LLM_BASE_URL` (unset disables), `LLM_MODEL` (required once the base URL is set), `LLM_API_KEY` (optional bearer token), `LLM_TIMEOUT` (per attempt, default `60s`), `LLM_VISION_MODEL` (optional; model for requests with images on the same endpoint, capability `llmVision`); partial config fails at startup. `llm.New` returns a `*llm.Client` or `llm.Disabled`; both implement `llm.Extractor` (`Extract`, `Enabled`). Requests go to `POST {base}/chat/completions` with `response_format: json_schema` (`strict: true`); schemas come from `llm.SchemaFor[T]` (every field required, only pointer fields nullable, so unknown text comes back as `""`; nullable objects and enums use `anyOf`; optional `llm:"desc=...,enum=a|b"` tag. Anthropic models allow at most 16 nullable fields per schema). Output that is not a JSON object or does not decode into `T` (`llm.ExtractAs`) is retried once; A request with `Request.Images` (`llm.Image{MediaType, Data}`) is sent to the vision model with the user message as a parts array (one `text` part when the input is non-empty, one `image_url` data URL per image); without a vision model it fails with `ErrVisionDisabled` before any call. Text requests keep the plain string content and the normal model. Errors are `ErrDisabled`, `ErrInvalidOutput`, `ErrRefused`, `ErrTruncated` (no retry) and `*APIError` (upstream `error.message` only). Never log prompts or model output or put them into errors. Tests use `llmtest.Fake`.

**Drafts:** `internal/drafts` is the source-agnostic draft inbox (model, store, handler). A draft has `status` (`pending|accepted|rejected`), `targetType` (`purchase|contract|cost|vehicle|contract_category|purchase_category|ledger_category|ledger_account|none`), `parentId` (category for purchase/contract, vehicle for cost, optional parent category for `ledger_category`; rejected with 400 for vehicle, contract/purchase category and ledger account), `input` (the module's create-input JSON), `source{kind,ref,title,url}` (kind `paperless|ledger|mcp|email`, `text` reserved), `note` (code the UI translates: `unclassified`, `empty_content`, `llm_invalid_output`, `llm_refused`, `llm_truncated`, `llm_request_rejected`, `currency_converted`, `currency_not_converted`, `recurring_payment`, `recurring_payment_ended`), `result{entityType,entityId}`. `Store.Create` fails with `ErrDuplicateSource` while a draft for the same source exists; `Decide` frees the source. Sources register `SourceHooks` on the handler: `OnAccept` runs before the draft is marked accepted (error → 500, draft stays pending), `OnReject` after. The accept `entityType` must equal the draft's `targetType` (any type but `none`). `Store.Counts` backs `GET /drafts/summary`. The classifier (`extraction.Targets`) is unchanged and never proposes the new types. Accept does not verify that the entity exists.

**Batch accept:** `POST /api/v1/drafts/accept-batch` (`drafts/batch.go`, `Handler.AcceptBatch`) takes `{ids, baseUrl}`: 1..100 (`MaxBatchSize`) distinct draft UUIDs and the origin of the UI (absolute http(s) URL without path, query, fragment or user info; a trailing slash is trimmed), otherwise 400 for the whole request. It is the only place where the drafts package creates entities, and it does so without importing modules: modules implement `DraftCreators() map[string]drafts.CreateFunc` (`draft_create.go` in contracts, purchases, auto and ledger; `categories.DraftCreator` for both category targets) and `internal/server` registers them with `Handler.RegisterTarget(target, moduleID, create)` plus `SetEnabled(coreStore.ModuleEnabled)` (`drafts` cannot import `module`, which imports it through `mcptool`). A `CreateFunc` gets `CreateRequest{EntityID, ParentID, Input}` and returns the entity's UI path (the same mapping as the frontend's `entityPath`; a cost entry's path is its vehicle's). It must return without creating when an entity with that ID exists, decodes the input strictly like `httputil.ReadJSON` (`drafts.DecodeInput`, an unknown field is `invalid_input`), runs the same `Validate` as the create endpoint and builds the entity with the constructor the create handler uses (the item targets get these steps from `drafts.NewCreateFunc(drafts.Creator[In]{Existing, CheckParent, Create})`) (`newContract`, `newPurchase`, `newVehicle`, `newCostEntry`, `categories.New`, `newLedgerCategory`, `newLedgerAccount`), so a change to a create endpoint applies to both. `ledger_category` takes its optional parent from the draft's `parentId`. Each draft is handled on its own, in request order: load (accepted → `already_accepted` with the stored result), `none` → `no_type`, module check, `entityID = drafts.EntityID(draft.ID)` (UUIDv5 in a fixed namespace, pinned by `TestEntityID_PinnedPerDraft`; changing the namespace would duplicate entities on a repeat), create, the source's `OnAccept` with `entityUrl = baseUrl + path`, `Decide`. The response is always 200 `{results: [{id, status: accepted|already_accepted|failed, code?, error?, entityType?, entityId?, warnings?}]}`; failure codes are `not_found` (also another user's draft), `rejected`, `no_type`, `module_disabled`, `parent_missing`, `parent_not_found`, `invalid_input` (the message of the create endpoint), `conflict` (duplicate IBAN), `source_link_failed` (hook error; the entity exists and the next attempt reuses it) and `internal_error` (logged with draft ID and step, fixed text). A failed draft stays pending. When the request context ends, the remaining drafts are left out of `results`. Known edge: if a draft is edited between a `source_link_failed` attempt and the repeat, the entity keeps the input of the first attempt. The single accept is unchanged and shares `Handler.accept` (hook, then `Decide`) with the batch. Tests: `drafts/batch_test.go` (fake creator and hooks) and `server/drafts_batch_integration_test.go` (all eight targets through the real app, messages compared with the create endpoints, paperless link/back-link/tags, repeat after a hook failure).

**Extraction:** `internal/extraction` is the shared classifier. `Classifier.EnabledTargets` / `LoadCatalog` build what the model may choose from (enabled purchase/contract/cost targets, categories and vehicles with IDs; module lookups through `extraction.Deps`, wired in `internal/server/extraction.go`, so the package does not import modules; which module a target belongs to comes from the modules' `DraftCreators`); `Catalog.Only(target)` forces one type. `Classify(ctx, operation, catalog, Input{Kind: InputDocument|InputNote|InputUpload|InputEmail, Title, Text}, now)` makes one `llm.ExtractAs` call (schema `{kind, confident, purchase?, contract?, cost?}`, each extract with `currency`; prompt per input kind with today's date; text truncated to 20k characters) and returns a `Proposal{Target, ParentID, Input, Note, Confident, Currency}` whose input has the module create-input shape. Unknown category/vehicle IDs, invalid dates, intervals, URLs and cost types are dropped or defaulted. `none`, empty text and `ErrInvalidOutput`/`ErrRefused`/`ErrTruncated`/LLM 400/413/422 give a `none` proposal with a note; other LLM errors are returned (transient; `IsTimeout` for timeouts). `Confident` is the model's flag and false without a valid parent or with a foreign currency. Non-EUR amounts are converted with `fx.Rates` at the purchase/cost date (today if missing, contracts always today), rounded to cents, original appended to `comments` (`USD 640.00 → EUR 572.86 (ECB 2026-10-30, 1 USD = 0.89509 EUR)`), note `currency_converted`; without a rate (disabled, unknown code, lookup failure) the amount is dropped, comment `USD 640.00 (not converted)`, note `currency_not_converted`.

**FX rates:** `internal/fx` looks up ECB reference rates from a Frankfurter-compatible API: `GET {FX_RATES_URL}/{date}?base={from}&symbols={to}` (default `https://api.frankfurter.dev/v1`; `off` disables, an empty value falls back to the default). Future dates are clamped to today; past-date rates are cached in memory; 10s timeout. `fx.Disabled` returns `ErrDisabled`. Consumers: the shared classifier (to EUR) and the ledger email-order matching (order currency to the transaction's currency); the server builds one instance for both.

**Quick add:** `internal/quickadd` handles `POST /api/v1/quick-add` with the classifier (operation `quickadd.classify`, note prompt). Stateless; the typed text is never logged. The same route accepts `multipart/form-data` (`upload.go`): `file` (required, at most `MaxFileBytes` = 10 MiB), optional `text` (a hint, same 2000 character cap) and `targetType`; unknown or repeated fields are a 400. The file type is sniffed from the bytes (`http.DetectContentType`), the client's content type and file name are ignored and never used. An image (JPEG, PNG, WebP) becomes `extraction.Input{Kind: InputUpload, Images}` with operation `quickadd.classify_image` and needs the vision model (the handler gets `vision` from `Config.LLMVisionEnabled()`). A PDF is read by `pdfText` (`pdftext.go`, on `github.com/ledongthuc/pdf`, pure Go): its own content-stream walk over at most 30 pages, 2 million operators and 100 kB of text, which inserts spaces from `TJ` gaps and from `Td` moves along a line measured against the font's glyph widths (kerning inside a word must not split it, a jump to a right-aligned amount must); parser panics are recovered. The text goes through the normal model as `InputUpload` (operation `quickadd.classify`); there is no OCR, so fewer than 20 letters or digits is `pdf_no_text`. Coded failures are `{"error","code"}`: 413 `file_too_large`, 415 `unsupported_file`, 409 `vision_not_configured`, 422 `pdf_no_text`, 422 `file_unreadable` (broken or encrypted PDF). Only the kind (`text|image|pdf`) and byte size of a request are logged, never the file name, content or extracted text (`TestUpload_LogsNoContent`). Known limit: the PDF parser inflates streams without a size cap, so a crafted PDF can cost CPU and memory; the route is JWT-only (`denied` for tokens).

**Paperless pipeline:** `paperless.Pipeline` (`PAPERLESS_PIPELINE_INTERVAL`, default `15m`, `0` disables; not started when the LLM is disabled). Per user with the pipeline enabled, paperless configured and at least one of purchases/contracts/auto enabled: find the inbox tag (never created by the pipeline), list tagged documents (oldest first, up to 500), skip documents that have a draft, fetch content for at most 10 new ones and classify each with the shared classifier (operation `paperless.classify`, document prompt; see Extraction). `none` proposals become `none` drafts with a note; transient LLM errors create no draft, stop the pass and are retried next time. `NewPipeline` takes the classifier and a user-ID lister (wired in `internal/server`). `paperless.Service` resolves a user's client and implements attach (links, back-link, done tag, optional tag removal) and detach (clears back-link, removes the done tag with the last link); `paperless.DraftHooks` uses it for accept (link must be stored, the rest is best effort → warnings) and reject (remove inbox tag). Tests use `paperless/paperlesstest` (fake paperless API) and `llmtest.Fake`.

**Email order extraction:** `ledger.EmailService` (`email_service.go`, `email_pipeline.go`, `email_extract.go`, `email_preclass.go`, `email_match.go`) turns messages into `LedgerEmailOrder`s with `llm.Extractor` (injected through `ledger.Config.Extractor`, nil = disabled). One shared path (`processMessages`) serves IMAP scans and `.eml` uploads: the IMAP scan selects the account's `folder` (required; modified UTF-7 encoded), fetches only headers (`BODY.PEEK[HEADER]`) of the newest 250 messages since `max(scanSince, lastScanAt−48h)` and downloads a message only when it needs extraction. Dedup runs before any LLM call: the key is the Message-ID (`mid:<hash>` when it is longer than 200 bytes or has control characters, `nomid:<hash>` without one); a message with an order (`idx/eord_msgid`) or a processed marker (`idx/eseen` with a reason: `not_order` for `isOrder=false`, `preclass` for pre-classified non-orders, `too_large` above 25 MB, `unreadable`, `unusable`) is skipped. `parseMessage` (`email_parse.go`) walks the MIME tree depth first (nested multiparts up to 10 levels, parts with `Content-Disposition: attachment` or a filename skipped), keeps the first `text/plain` and `text/html` body, decodes the transfer encoding (base64 leniently: whitespace dropped, missing padding accepted) and the part's `charset` to UTF-8 (WHATWG labels, unknown charsets keep the bytes), and strips the HTML when there is no plain text. `extractOrder` sends sender, subject, date and the text body (cap 12 000 characters) with the system prompt that treats the email as untrusted data; `validateExtraction` checks total, currency, date (falls back to the Date header), payment method enum, items. Failures: `llm.ErrDisabled` → `ErrEmailLLMDisabled` before anything is downloaded (409, scheduler status "skipped"); invalid/refused/truncated output (`isUnusableLLMOutput`) and a result that fails validation → per-message warning, no marker, retried next scan, and counted in `idx/efail/{accountId}/{dedupKey}` (`handleFailedExtraction`): at `LEDGER_EMAIL_MAX_EXTRACTION_FAILURES` (default 3, at least 1; `ledger.Config.EmailMaxExtractionFailures`) the message is marked `unusable` with one warning ("ignored from now on") instead and later scans skip it without an LLM call; the counter is deleted in the transaction that stores the order or sets any processed marker (`CreateScannedLedgerEmailOrder`, `MarkLedgerEmailsSeen`) and with the account, uploads count like scans; a rejected request (non-transient 4xx such as 400, 404, 422) → warning "LLM request was rejected", no marker, not counted (it may be a configuration error such as a wrong model name), retried at every scan inside the lookback window; transient errors → warning and `skipped`, not counted, three in a row stop the scan as `partial`; IMAP I/O errors abort the scan (the connection is unusable), a tagged `NO` on a fetch only skips the message and makes the scan incomplete, but after 3 refusals of the same message (counted in `idx/erej/{accountId}/{key}`, `uid:N` for header fetches) it is marked `unreadable` and ignored; context end stops the scan and keeps stored orders. Warnings and logs contain only message labels (`uid N`, file names) and fixed texts, never email content or model output. `deriveMatchRule` (pure) gives the counterparty pattern and charge window from merchant and payment method (PayPal `paypal` −3/+7; merchant containing `amazon` without PayPal `amazon` −3/+60; otherwise the quoted merchant −3/+30; a merchant shorter than 3 characters or none → no auto-link); `matchRuleForOrder` keeps legacy importer orders unchanged. Amounts are compared per transaction currency (`autoLinkOrder`): transactions in the order's currency must match exactly (alone or as a split payment of up to 4); only when none does, transactions in another currency (a USD order paid from an EUR account) are compared with the order total converted by `fx.Rates` (`ledger.Config.Rates`, nil = disabled) at the order date, and exactly one within ±5 % (`fxToleranceBasisPoints`, conversion fees and rate drift) is linked with the warning `linked by converted amount`; several give `multiple converted transaction matches` and no link, and converted amounts are never combined into split payments. Without a rate (FX off, unknown currency, lookup failure) the order is stored unmatched without a warning and is not retried. Stored orders always keep the extracted currency and total; all currencies are treated as two-decimal minor units. New orders have `importerId: "llm"`. Optional per-account `preClassify` first sends sender and subject of batches of 40 (fail open: anything the model does not clearly reject is extracted). **Scan jobs** (`email_job.go`): `EmailService` keeps one `LedgerEmailScanStatus` per account in memory (`state` `idle|running|done|partial|failed`, `trigger` `manual|scheduled|upload`, timestamps, counts, warnings, `error`, `resumes`); the entry in state `running` is the account's scan slot, so there is one scan per account at a time (`ErrEmailScanRunning`), and the last finished one stays readable until the next scan or a restart. `StartScan` (manual) takes the slot and scans in a goroutine bound to the module's background context and `emailScanTimeout`; scheduled scans (`scanMailbox`) and uploads (`ScanUploadedMessages`) block their caller and use the same slot. The pipeline publishes the counts after every header and message (`publishScan`). The account's scan fields are written while the slot is still held (`runScan`'s `record` callback), so a client that sees a scan finished reads the updated account; a failed manual scan also stamps the attempt and stores `Scan of folder … failed`. `partial` covers the time limit, a stop after repeated LLM failures and skipped messages. **Resume:** a scan that ended at the time limit or after repeated LLM failures stores `ScanResumePending` on the account (every attempted scan sets or clears it); `accountDue` then uses `emailScanResumeDelay` (5 min) instead of the interval and the scheduler ticks at `min(interval, 5 min)` (`emailSchedulerTick`), with no cap on consecutive resumes. With the scheduler off nothing resumes and `resumes` stays false. `LastScanAt` (the lookback anchor) only advances after a complete IMAP scan (no `partial`, no `skipped`); `LastScanAttemptAt` is stamped by every attempted scan and schedules the next background scan, so failed or incomplete accounts keep the normal interval while accounts skipped for a missing folder/LLM stay due each tick. Scan state is written with `SetLedgerEmailAccountScanState`, which changes only the scan fields, so edits made during a scan are kept (and account edits go through `ModifyLedgerEmailAccount`, one load-modify-store transaction); changing host, port, username, TLS, folder or the password clears `LastScanAttemptAt` and `ScanResumePending` so the next tick rescans; racing transactions are retried on `badger.ErrConflict`; uploads never move `LastScanAt`. **Folder list:** `imapClient.ListFolders` sends `LIST "" "*"` and `parseIMAPListLine` reads each answer (flags, delimiter, mailbox as atom, quoted string or literal): `\Noselect`/`\NonExistent` mailboxes and names the account could not store (`normalizeEmailFolder`) are left out, names are decoded from modified UTF-7 (`decodeIMAPMailboxName`, the inverse of `imapMailboxName`; an invalid name is kept as sent) and keep the server's hierarchy delimiter, at most 2000 folders. `EmailService.ListFolders` returns `ErrIMAPLogin` for a refused login (a tagged `NO`/`BAD`, `errIMAPCommandFailed`) and `ErrIMAP` otherwise. Tests use `llmtest.Fake` and the fixtures in `docs/design/email/`.

**Email drafts:** `ledger.EmailDraftPipeline` (`email_draft_pipeline.go`; built when `ledger.Config.Drafts` and `ledger.Config.Classifier` are set, started from `StartBackground` on `LEDGER_EMAIL_SCAN_INTERVAL`, not started with interval `0`, without an encryption key or without the LLM) is the `email` draft source. `RunUser` (one run per user, `ErrEmailDraftsBusy`; `ErrEmailLLMDisabled` without the LLM, `ErrEmailDraftsNoTargets` when none of purchases/contracts/auto is enabled; the scheduler only runs users with the ledger module enabled) goes through the accounts that have a `draftsFolder` (optional, validated to differ from `folder`): `openMailbox` selects it, `UID SEARCH SINCE scanSince` (no `lastScanAt` anchor, the newest 250), and `listMessages` (the header-first listing shared with the order scan, `headerListing` holds the scan-specific steps) fetches only headers. A message is skipped when it has a draft marker (`idx/dseen`) or a pending draft (`HasSource`); at most 10 new messages per user and pass are downloaded and classified with `extraction.Classify` (operation `ledger.email_draft`, `InputEmail`: the text is `buildEmailInput`, i.e. sender, subject, date and the plain-text body capped at 12 000 characters, with a system prompt that treats the email as untrusted data). The draft has source `email`, ref `{accountId}:{dedupKey}` (`emailDraftRef`/`parseEmailDraftRef`), the subject as title (sender as fallback) and no URL; `edmsg/{accountId}/{key}` keeps Message-ID (only when it is the dedup key, i.e. not hashed), subject, sender and date for the accept hook. `none` proposals (also unusable LLM output, which the classifier maps to a note) become `none` drafts. Failures: a transient LLM error creates no draft and ends the pass (retried next time); a message that is too large or cannot be parsed gets a marker (`too_large`, `unreadable`); a fetch the server refuses is counted in `idx/erej/{accountId}/drafts/{key}` and ignored after 3 refusals; an IMAP error ends that account with the warning `<account name>: could not read the drafts folder` and the next account continues. `EmailDraftRunResult{found, created, skipped, failed, warnings}`. `EmailDraftHooks` (`email_draft_hooks.go`, `(*Module).EmailDraftHooks()`, registered for `drafts.SourceEmail` in `internal/server`): accept writes the email link (`elink/…`), the `accepted` marker and deletes `edmsg` in one badger transaction (`AcceptLedgerEmailDraft`; an error keeps the draft pending); a deleted account or missing message data only gives a warning, and a draft accepted as another type than contract, purchase or cost is marked without a link. Reject sets the `rejected` marker. Neither hook waits for the mail server: with an action for the drafts folder they queue it in the same transaction and call `emailActions.Kick` (see **Processed emails**). Deleting an account removes its markers, pending message data and email links (`deleteLedgerEmailDraftData`); pending email drafts of a deleted account stay in the inbox and can still be decided. Logs carry counts, account IDs and `uid N` labels only, never subject, sender or body (`TestEmailDrafts_EndToEnd` checks the LLM input and the log). Tests use the fake IMAP server (`email_fake_imap_test.go`, `addFolder` serves a second folder) and `llmtest.Fake`.

**Processed emails:** `emailActions` (`email_actions.go`, one per module, shared by `EmailService`, `EmailDraftPipeline` and `EmailDraftHooks`) moves or deletes processed messages in the mailbox when the account asks for it; without an action (`keep`, the default and what an empty field means) no write command is ever sent. **Queue:** `queueLedgerEmailAction(s)` (`store_email_pending.go`) writes `idx/epend/{accountId}/{o|d}/{dedupKey}` (`ledgerEmailPending`: UID, UIDVALIDITY, `attempts`, `at`) inside the transaction that stores the local result, and only while the folder's action is `move` or `delete` at that moment: `CreateScannedLedgerEmailOrder` (with the message's `emailMailboxRef`; nil for uploads), `MarkLedgerEmailsProcessed` (`not_order`, `preclass`; `MarkLedgerEmailsSeen` stays for `too_large`, `unreadable`, `unusable` and queues nothing), `AcceptLedgerEmailDraft` and `DecideLedgerEmailDraft` (UID and UIDVALIDITY come from `edmsg`; a draft without them is found by Message-ID). So nothing reaches back to messages processed before the action was set. **Drain:** `drain(ctx, client, userID, accountID, source)` runs on a client that has the source folder selected: at the end of `scanFolder` and of `EmailDraftPipeline.runAccount` (skipped after an IMAP I/O error or when the context ended), and from `Kick(userID, accountID)`, which the draft hooks call after a decision (own connection, `emailActionKickTimeout` 30 s, coalesced per account, bound to the module's background context, needs the encryption key; failures there are only logged and left to the next pass). It reloads the account, so the action is the current one: `keep` clears the queue, a move without target or a client on another folder than the account's does nothing. Each record is located by `locateEmail`: the stored UID counts only with the same UIDVALIDITY and after `BODY.PEEK[HEADER]` gave the record's dedup key; otherwise `UID SEARCH HEADER Message-ID` for a verbatim Message-ID key (not `mid:`/`nomid:`), every hit checked the same way. A UID is never acted on unverified. Not found: the record is dropped (silently for a Message-ID key, the user moved or deleted the message; counted as "could not be found" for a hashed key). **Commands** (`email_imap.go`): `Move` is `UID MOVE` with the `MOVE` capability, else `UID COPY` + `UID STORE +FLAGS.SILENT (\Deleted)` + `UID EXPUNGE`; `Delete` is the last two. `delete` moves to `TrashFolder()` (the mailbox with the `\Trash` flag in `LIST`, RFC 6154) unless there is none or it is the scanned folder; a refused `LIST` deletes nothing in that run. Without `UIDPLUS` the message stays flagged (`errIMAPNotExpunged`, record dropped, warning): a plain `EXPUNGE` is never sent because it would remove everything else the user flagged. Folders are never created. **Failures:** a tagged `NO`/`BAD` counts in `attempts` (`RecordLedgerEmailPendingFailure`) and the record is dropped at `maxEmailActionAttempts` (5); an I/O error ends the drain and counts nothing. Warnings (`emailActionResult.warnings`) are fixed texts with counts, added to the scan result or the pass (`<account name>: …`), and never make a scan `partial`; logs carry IDs and counts only. The status word of a tagged response is parsed (`imapTaggedOK`), a `NO` whose text contains "OK" is a failure. Imported accounts keep their actions (actions are not validated on import): an unknown action is treated as `keep`. Tests: `email_actions_test.go`, `email_imap_actions_test.go`, `store_email_pending_test.go`; the fake IMAP server keeps per-folder messages and `\Deleted` flags, records every command (`sent`), and has `capabilities`, `uidValidity` and `setRefuse(prefix, on)`.

**Ledger package layout:** the store is split by topic: `store.go` (the `Store` type, shared helpers and `retryConflicts`, which is `storage.RetryConflicts` with 3 attempts on the caller's context without its cancellation, so a scan at its time limit still records what it found), `store_keys.go` (the key builders of accounts, categories, transactions, imports, email accounts and orders), `store_account.go`, `store_category.go`, `store_txn.go` (load, list, filter, page, details, search, review), `store_txn_ref.go` (references and the `link.TransactionSide`), `store_transfer.go` (manual transfer candidates, link and unlink; the automatic linking is `store_transfer_detect.go`), `store_import.go`, `store_email_account.go` (accounts, scan state, seen/reject/failure counters) and `store_email_order.go`, next to the feature stores (`store_bank.go`, `store_balance.go`, `store_split.go`, `store_suggestion.go`, `store_recurring.go`, `store_email_draft.go`, `store_email_pending.go`, `store_categorize.go`, `store_analysis.go`). Records are read and written with `storage.Get`/`List`/`SetJSON`; store methods pass their context on. The handlers follow the same topics: `handler_accounts.go` (account CRUD, the account transaction list, balances), `handler_categories.go`, `handler_transactions.go` (details, splits, references, transfers), `handler_review.go` (review queue, single and batch review), `handler_imports.go` (preview, commit, import list), `handler_suggestions.go`, `handler_email.go`, `handler_email_draft.go`, `handler_bank.go`, `handler_recurring.go`, `handler_analysis.go`. The import handlers answer through `importError`: an `importInputError` (unknown source type, unreadable or unparsable file, invalid account choice) is 400 with its text, everything else goes through `storeError` (missing preview or account 404, expired preview 410, duplicate file 409, store failures 500 "internal error"). The validation errors `storeError` maps to 400 are sentinels (`ErrLedgerLinksInvalid`, `ErrLedgerReferencesInvalid`, `ErrLedgerScanSinceInvalid`, `ErrLedgerTransactionIDsEmpty`, besides the `storage` ones), compared with `errors.Is`. The bank service is `bank_service.go` (type, errors, bank list, session close), `bank_auth.go` (consent start, callback, session storage), `bank_connections.go` (connection list, IBAN and explicit mapping, disconnect) and `bank_sync.go`. Shared helpers: `userRunner` (`user_runner.go`, embedded by `CategorySuggester`, `RecurringService` and `EmailDraftPipeline`) allows one run per user (`tryLock`/`unlock`, `Running`) and starts background runs on the server's WaitGroup and context with a timeout (`goBackground`); `runTicker` (`scheduler_loop.go`) is the pass-then-tick loop of the email scan scheduler, the email draft pipeline and the bank sync scheduler (each keeps its own tick and disable checks); `accountPassword` (`email_service.go`) decrypts a stored IMAP password (`ErrEmailPasswordMissing` without one). Import previews live in memory for 15 minutes (`PreviewCache`); `RunCleanup`, started from `StartBackground`, drops expired ones once per TTL.

**Deleting a ledger account:** `Store.DeleteLedgerAccount` (`store_account.go`) first unmaps every bank account mapped to it (sync state reset, `unmapped` not set, so a new account with the same IBAN is mapped again and its first sync uses `strategy=longest`). It then deletes the account's transactions found through `idx/acc_txn/{accountId}/` in chunks of 200 (`deleteAccountChunk`, one badger transaction each, retried on conflicts) and finally, once none is left, the import batches of the account (`imp/`, `idx/imp_txn/`, the `idx/file_hash/` entry, so the files can be imported again), its balance snapshots (`bal/{accountId}/`), the `idx/acc_iban/` entry and the account record. An interrupted delete can be repeated and continues. Per transaction: its references are removed on the target side through the link registry, a transfer partner in another account loses the pair (`clearLedgerTransferState`, back to review without category), linked email orders drop the transaction and become `unmatched` when none is left, the `idx/txn_fp/` entry (only when it points at the transaction), `idx/xabs/{txnId}` and the `idx/xdup/` entry it names (an absorbed API row becomes importable again), `sug/{txnId}`, the index entries and the transaction. Paperless links of deleted transactions stay as unreachable keys like those of every other deleted entity; recurring-payment records keep their transaction IDs (accepting their draft warns about missing transactions). `CommitLedgerSync` checks inside its transaction that the target ledger account still exists, so a sync that was already fetching when the account was deleted fails for that account instead of creating orphans. The handler runs the delete with a context that is not cancelled with the client (5 minute timeout). `UpdateLedgerAccount` changes name and bank only.

**Account balances:** a balance snapshot (`model_balance.go`, `store_balance.go`, `bal/{accountId}/{asOf}`) is the balance at the end of day `asOf` and includes every transaction booked on or before it; one per account and day, a later write replaces it whatever the source. The newest snapshot is the anchor, so an older CSV imported later only adds history. `computeLedgerAccountBalance` derives `LedgerAccountBalance` from the snapshots and the account's transactions (loaded through `idx/acc_txn/`): `currentMinor` = anchor + the transactions booked after `asOf`; `driftMinor` (only with an earlier snapshot) = anchor − (previous snapshot + the transactions booked after it up to the anchor's `asOf`), computed on read and never stored, so it is current after any later import; anything but zero means transactions are missing, duplicated or skipped. A transaction booked on `asOf` after the snapshot was taken counts as included (known limit, the next snapshot shows it as drift). Splits, transfers and categories do not matter, only `amountMinor`. `Store.ListLedgerAccountTransactionsPage` pages an account's transactions in list order by offset (with the total count) and derives the page balances from `currentMinor`: `closing` = current − the transactions listed above the page, `opening` = closing − the page's transactions (one scan, like the plain list). **Sources:** CSV imports (`import_balance.go`): `ParseResult.Balance` → `PreviewResult.balance` (`{amountMinor, asOf}`, shown in the preview) → `CommitLedgerImportWithBalance` stores the snapshot (source = the file's source type) in the import's badger transaction. DKB: the preamble line `Kontostand vom DD.MM.YYYY:` (date from the label, `DD.MM.YY` accepted); it is taken as the booked balance, although DKB's pending rows are imported (unverified, may show as drift). comdirect: `Neuer Kontostand` from the header; `asOf` = the end of an absolute `Zeitraum: DD.MM.YYYY - DD.MM.YYYY`, otherwise (`30 Tage`, the export date is not in the file) the newest booking date; `Alter Kontostand` from the footer is only a check: when it plus the parsed rows (pending `offen` rows are skipped) differs from the new balance, the preview gets the warning `balance: … differs from Neuer Kontostand by X EUR`. A balance can also be set by hand (source `manual`, only manual snapshots can be deleted, `ErrLedgerBalanceNotManual` → 409). A missing balance line means no snapshot; an unreadable one is a `balance:` warning and never fails the import. Snapshots are exported (`balances`, optional, so older exports still import; snapshots of accounts that are not in the export are skipped with a warning).

**Transaction splits:** a ledger transaction can carry `splits` (`model_split.go`, `store_split.go`): parts with `amountMinor`, `categoryId` and an optional `note`, booked to another category than the transaction's own (e.g. a cash withdrawal inside a supermarket payment). The bank row stays one transaction (amount, fingerprint, dedup, cross-source absorption and bank sync never look at the parts); what the parts leave (`ledgerSplitRemainder`) keeps the transaction's `categoryId`. `normalizeLedgerSplits` is the one validation: at most 10 parts (`maxLedgerSplits`), every part has a category, a non-zero amount with the transaction's sign and a trimmed note of at most 500 runes, and together the parts stay strictly below the transaction amount (a remainder is always left). `SetLedgerTransactionSplits` replaces the list in one badger transaction, checks that the categories exist and leaves category, review state and everything else alone; linked internal transfers are refused (`ErrLedgerTransferLinked`), and linking a transfer clears the parts (`applyLedgerTransferState`). Deleting a category clears it from the parts (`clearLedgerSplitCategory`; the part keeps its amount without category) and sets the transaction back to `needsReview`, like the main category. `LedgerTransactionListOptions.CategoryID` matches the main category or a part (`hasLedgerCategory`). Splits are exported with the transaction; the import drops the whole split of a transaction whose parts are invalid, name a category that is not imported or belong to a linked transfer (`sanitizeImportedSplits`, one warning with the count; a part without category is kept). Review, batch review, keyword matching, suggestions and recurring detection only work on the main category and amount.

**Ledger analysis:** the analyses (`analysis.go`, pure; `store_analysis.go`, `handler_analysis.go`) are read-only `GET`s under `/api/v1/ledger/analysis/`. A handler loads accounts, categories and transactions in one read transaction (`LoadLedgerAnalysisData`, one scan of `txn/`, no per-transaction lookups) and calls one pure function; nothing is stored or cached. **Range:** `from` and `to` are inclusive booking dates and both optional: `to` omitted = today (UTC; `Handler.now` pins it in tests), `from` omitted = the earliest booking date (of the account when `accountId` is given), or `to` when there is none or it lies after `to`; the response carries the effective `from` and `to`. The dates are honoured exactly, a range that starts or ends mid-month has a partial first or last month and nothing is snapped. Months come from `bookingDate` by integer arithmetic on the string (no `time.Time`, no timezone), ascending and gap-free with zeros; a booking date that is not `YYYY-MM-DD` is skipped. `from > to` and more than `maxLedgerAnalysisMonths` (1200) calendar months are 400 (`ErrLedgerAnalysisInvalid`); the bound also applies to an omitted `from`. **What counts** (`eachCountedLedgerTransaction`): transactions booked inside the range, except linked internal transfers (`specialCategory` `internalTransfer` or a transfer pair) and other currencies. A transaction's currency is the account's when that is not EUR, else its own, else EUR (`ledgerAnalysisCurrency`); there is no conversion, left-out currencies of in-range non-transfer transactions are reported as `excludedCurrencies` (sorted, upper case). Unreviewed transactions count under the category they carry. A transaction that only has the regular category "Transfers" without a link counts like any other. **Roll-up** (`ledgerCategoryTree`): split parts count under their own category and the remainder under the transaction's (`eachLedgerPart`), each rolled up to its top-level ancestor. A category whose parent does not exist is its own top level, and so is every category on or below a parent cycle. An amount without a category, or with an ID that names none, goes to the uncategorized series (never dropped). **Netting:** the signed amounts are summed per series and month (`ledgerNets`). In the top-level view a negative net is that category's spending (returned positive, `max(0, -net)`), so a refund lowers it and a month with a positive net is 0; a series is listed when it has any spending. **Spending** (`AnalyzeLedgerSpending`): columnar `{from, to, months, series: [{kind, categoryId?, name, amountsMinor, totalMinor}], totalsMinor, excludedCurrencies}`, all arrays non-nil; `kind` is `category`, `uncategorized` (no ID, empty name) or `direct`; `totalsMinor` is the sum of the listed series per month; series are ordered by total descending, then categories before the others, then name (case-insensitive), then ID. **Subcategory view** (`parentCategoryId`, must be a top-level category): one series per direct child (deeper descendants rolled up into it) plus `direct` for amounts booked on the parent itself (`categoryId` = the parent). Its values are **signed** (`-net`): a child with a net inflow in a month is negative there and is not clamped, so `totalsMinor` equals `-net` of the parent, which is the parent's value in the top-level view for every month in which the parent is spending. A series is listed when any month is non-zero. Validation errors name only the parameter; nothing is logged on success and no counterparty, purpose, IBAN or amount reaches a log line or an error body (`TestLedgerAnalysis_LogsNoTransactionData`). **Cash flow** (`AnalyzeLedgerCashFlow`, `from`/`to` only): from the same top-level nets, per month `expensesMinor` = the sum of the negative nets (so it equals the spending view's `totalsMinor` by construction), `incomeMinor` = the sum of the positive nets, `netMinor` = income − expenses = the sum of all counted amounts of the month (`TestLedgerAnalysis_SpendingMatchesCashFlow` pins all three against an independent roll-up). Income booked under a category that is spending on balance lowers that category's spending instead of showing as income, and the other way round. **Ranking** (`AnalyzeLedgerRanking`, `from`/`to` only): `categories` rank the categories by what is booked **on them** (`ledgerOwnCategoryNets`: split parts and remainders under their own category, no roll-up, so a parent only counts amounts booked on itself and the leaves are ranked on their own; netted and clamped per month like the top-level view, uncategorized as its own entry); an entry carries `parentName` (the direct parent's name) unless it is a top level. `counterparties` net the **whole** transaction amount (splits do not matter) per counterparty name over the range; the group key is the name lower-cased with whitespace collapsed, transactions without a name form one entry with `unknown: true` and an empty name. Only groups with net spending are listed (refunds reduce, a net inflow drops the group), with the spelling of the newest transaction of the group (ties: the smaller name), ordered by amount descending, then key. Both lists are cut to `ledgerRankingLimit` (10). The counterparty loop runs over the transactions already in memory, the store is still scanned once per request. `TestLedgerAnalysis_FiveThousandTransactions` runs every endpoint over 5000 stored transactions (bound 2 s); `BenchmarkAnalyzeLedgerSpending` measures the pure function (`go test ./internal/modules/ledger -run '^$' -bench AnalyzeLedger`).

**Net worth series:** `AnalyzeLedgerNetWorth` (`analysis_networth.go`, pure; `LoadLedgerNetWorthData` reads accounts in list order, transactions and all balance snapshots in one read transaction) returns `{from, to, dates, totalMinor, accounts: [{accountId, name, valuesMinor}], excludedAccounts: [{accountId, name, reason, currency?}]}`, all arrays non-nil. **Included** are EUR accounts (an empty currency counts as EUR) with at least one balance snapshot; every other account is in `excludedAccounts` with `reason` `currency` (with its `currency`; wins when both apply) or `no_balance` and counts neither in `accounts` nor in the total, never as 0. Unlike the category analyses it uses every transaction of an included account (linked transfers too), only `amountMinor` matters. **Range:** as for the other analyses (`from`/`to` optional, 400 for `from > to` or more than 1200 months); `from` omitted = the earliest of the first snapshot `asOf` and the first booking date over the included accounts. **Points** (`ledgerNetWorthDates`): every month-end `d` with `from <= d < last`, then `last = min(to, today)`; a range inside one month is that one point, a range that starts after today is the single point at today, and without an included account there are no points (`from`/`to` are still set). **Value at a date** (`ledgerBalanceAt`): the newest snapshot at or before the date plus the transactions booked after its `asOf` up to the date; before the account's first snapshot, that snapshot minus the transactions booked after the date up to its `asOf` (a booking on a snapshot's day counts as included in it). Per account the transactions are sorted once into prefix sums (`bookedSums`), each point is two binary searches. **Last point:** when `to` is today or later (or omitted) the last value is `computeLedgerAccountBalance(...).CurrentMinor`, so it equals `balance.currentMinor` of `GET /ledger/accounts` including bookings dated after today (`TestLedgerNetWorthEndpoint_LastPointIsCurrentBalance`); the frontend's dashboard card relies on that. **Drift is not corrected:** where two snapshots disagree with the transactions between them, points before the later snapshot's `asOf` follow the earlier snapshot and points from that day on follow the later one, so the drift shows as a jump at the later snapshot (`TestAnalyzeLedgerNetWorth_Drift`). Before an account's first booking the line is flat at the computed opening balance; an account opened inside the range does not start at zero. Nothing is logged; the log test covers this endpoint as well.

**Keyword matching:** `MatchFields` (`categorization.go`) picks the category for a counterparty and purpose: a match word is a case-insensitive substring of `counterparty + "\n" + purpose`; the longest matching word wins, then the deeper category, then the name. Some banks (comdirect) wrap the purpose into fixed-width lines joined with `; `, which can split a word (`Twitch I; nteractive`) or swallow the space between two words (`Deutsche; Post AG`), so when the text contains `; ` the word is also looked for in the variants with the breaks removed and replaced by a space (other spaces stay, so a word never matches across a plain space). The import (CSV and bank sync) and the suggestion run use it.

**Automatic transfer linking:** `Store.AutoLinkLedgerTransfers` (`store_transfer_detect.go`) runs synchronously at the start of `Handler.afterImport` (CSV commit and bank sync, 30 s timeout, before the suggestions start, so they never categorize a transfer; a failure is a warning and the suggestions still run). In one badger transaction (conflicts retried) it links the pairs `detectLedgerTransferPairs` finds: both transactions are not `confirmed`, not linked and without splits; each is the other's only match under `isPotentialLedgerTransferMatch` (opposite amount, another account, same currency, ±3 days, value date or else booking date), counted over all transactions, so a reviewed look-alike makes the pair ambiguous; and either side names the other's account IBAN as counterparty IBAN (`ledgerTransferIBANMatch`, normalized) or both have the same counterparty name (case and whitespace ignored). Linking is `applyLedgerTransferState` on both sides, like the manual link (category and splits cleared, special category `internalTransfer`, `confirmed`, source `manual`). Reviewed transactions are never touched; link them by hand. Logs carry the pair count only.

**Category suggestions:** `ledger.CategorySuggester` (`categorization_llm.go`, `store_suggestion.go`, `handler_suggestions.go`) proposes ledger categories with `llm.ExtractAs` (operation `ledger.category_suggest`, same `ledger.Config.Extractor`). A candidate is `needsReview`, uncategorized, without special category or transfer pair, with counterparty or purpose. A run first re-applies `MatchFields` with the current categories: a match sets the category with source `keyword` (still `needsReview`) and is never sent. Candidates with a stored suggestion are skipped, except when its category was deleted, or when it is a marker without category (model found nothing) and a category was created or updated after it. Candidates go newest first, `LEDGER_SUGGEST_BATCH_SIZE` per call (default 25, 1..100) and at most `LEDGER_SUGGEST_MAX_PER_RUN` per run (default 100, ≥ batch size; invalid values fail at startup); `remaining` reports the rest. Input: numbered category paths, examples (reviewed transactions whose counterparty shares a word of at least 3 characters, no stop words or numbers; 3 per transaction, 30 per batch), and numbered transactions (booking date, amount + currency, counterparty 200 / purpose 300 runes). Output `{index, categoryNumber (0 = none), confidence high|medium|low, matchWord}`: out-of-range or duplicate indexes are dropped, an unknown category becomes a marker; a match word is kept only when it is 3..64 runes, has no comma, is not only digits, is a case-insensitive substring of the transaction's counterparty/purpose (so the rule catches it), is not a match word already and is not proposed for two categories in one batch. Storage `sug/{txnId}`; `PutLedgerCategorySuggestions` and `ApplyLedgerRuleMatches` re-check the candidate state inside the write transaction; `ReviewLedgerTransaction` deletes the suggestion; the review queue only shows suggestions of candidates whose category exists. Errors: `ErrDisabled` → `ErrSuggestLLMDisabled` (409); invalid/refused/truncated output and 4xx → warning, the batch is retried next run; transient errors and context end → `partial`, the run stops and keeps what it stored. One run per user (`ErrSuggestRunning`, 409; `userRunner`); `RunInBackground` is called after every successful import commit (no-op without LLM or while a run is going), bounded by the module's background context and a 5 minute timeout like the manual run (which is not cancelled when the client disconnects). Logs carry counts only.

**Recurring payments:** `ledger.DetectRecurring` (`recurring.go`, pure) finds recurring outgoing payments; `ledger.RecurringService` (`recurring_service.go`, `store_recurring.go`, `handler_recurring.go`) proposes them as `contract` drafts (source kind `ledger`). Candidates: negative amount, currency `EUR` (case-insensitive; an empty currency is skipped, the importers always set one), no internal transfer or transfer pair. Counterparty key: `counterpartyTokens` of the name joined with spaces, else `iban:` + the upper-cased IBAN without spaces, else skipped. Per key, in booking-date order (ties by ID), a payment joins the first chain whose last amount is within max(10 %, 100 cents) of it, otherwise it starts a new chain (splits PayPal-like counterparties by amount, keeps gradual price increases together). The median gap in days picks the interval: monthly 26–35 (≥ 3 payments), quarterly 80–100 (≥ 3), yearly 350–380 (≥ 2); at least 80 % of the gaps must lie in that window (so one missed month needs at least 5 other regular gaps). A chain containing a transaction already linked to a contract is dropped, so an accepted group is not proposed again when new payments arrive. A group carries the latest counterparty name (IBAN fallback), interval, the latest amount as price, first and last booking date, `ended` (last payment older than today − 2 intervals) and the transaction IDs; `ref = hex(sha256(key|interval|firstTxnID))[:32]`, stable while the series grows. A run (`RunUser`, one per user, `ErrRecurringRunning` → 409; `ErrTargetModuleDisabled` → 403 `module_disabled` while contracts is disabled; without a draft store 409) skips groups with a pending draft (`HasSource`) or a `rejected` record, writes `recur/{ref}` (`{transactionIds, status: pending, createdAt}`) and then the draft: input `{name, company, price, billingInterval, startDate, endDate?}` (`endDate` = last payment when ended), no parent (the user picks the category in the inbox), title `<name> · <n>× <amount> EUR`, no URL, note `recurring_payment` or `recurring_payment_ended`. At most 20 new drafts per run and 50 pending ledger drafts (`CreateLimited`; the run stops at the cap). A pending record without a draft (the create failed) is overwritten by the next run. `RunInBackground` runs after every successful import commit (no-op while a run is going), bounded by the module's background context and a 2 minute timeout like the manual run. Hooks (`RecurringDraftHooks`, `(*Module).DraftHooks()`, registered in `internal/server`): accept checks that contracts is enabled, links all recorded transactions to the new contract in one badger transaction (`LinkLedgerTransactionsToTarget`; an unknown contract → error, the draft stays pending; missing transactions → a warning with their count) and deletes the record; without a record it only warns. Reject sets the record to `rejected` (creating it if missing). Logs carry counts only.

**Bank import:** `internal/enablebanking` is the HTTP client: RS256 application JWT (`kid` = app ID, `iss enablebanking.com`, `aud api.enablebanking.com` as a plain string (an array is rejected with 401), one hour, cached until 5 minutes before expiry, clock injectable), `ASPSPs`, `StartAuth`, `CreateSession`, `SessionStatus`, `DeleteSession`, `Transactions`, `Balances` (`GET /accounts/{uid}/balances`, the ISO 20022 balance types with dates kept as text); responses are read through a 10 MiB limit, 30 s default timeout, no retries. Errors never carry upstream message text, URLs or key material: `APIError{Status, Code}` keeps only the upstream `error` code if it matches `^[A-Z_]{1,64}$`, `TransportError` keeps only the cause of the `url.Error` (the URL contains session IDs and account UIDs); classifiers `IsRateLimited`, `IsSessionUnusable`, `IsAccountNotAccessible`, `IsAppAuth`, `IsWrongTransactionsPeriod`, `IsUnavailable`, `IsBalanceAccessMissing` (403 or `ACCESS_DENIED`, not a lost session: a consent without balance access). `enablebankingtest.New(t)` is the in-memory fake API (JWT verification on every request, rejecting an array `aud` like the real API, `AllowCode`, `SetTransactions`, `SetBalances` (empty list when unset), `SetPageSize`, `FailNext`/`FailAlways`/`FailTransactionRequest`, recorders for auth requests, session calls, transaction queries and balance calls). The ledger side (`ledger.BankService`, `bank_service.go`, `bank_sync.go`, `bank_scheduler.go`, `bank_notify.go`, `bank_convert.go`, `bank_window.go`, `store_bank.go`, `handler_bank.go`) works like this:
- **Consent:** `StartAuthorization` checks `PUBLIC_URL` and the bank (`GET /aspsps?country=<CC>&psu_type=personal&service=AIS`, cached 10 minutes per country; `verified` = name contains `dkb` or `comdirect`), stores a single-use state and posts `/auth` with `valid_until = now + min(maximum_consent_validity, 180 days) − 5 min` (90 days without a maximum), `balances`, `transactions` and `transactions_extended_history` access, `psu_type personal` and the redirect URL `PUBLIC_URL/api/v1/ledger/bank/callback`. The state is `base64url(AES-GCM(userID + "." + 128 random bits))`: unforgeable without `ENCRYPTION_KEY`, no global index, nothing about the user reaches the bank. `bstate/{sha256(state)}` is consumed in one badger transaction (unknown, used or expired state = `ErrBankStateInvalid`, TTL 15 minutes).
- **Callback (public):** `GET /api/v1/ledger/bank/callback` is registered on the outer mux, not in the scope table. It never reads `Authorization`, is not rate limited (a forged state fails at AES-GCM before any DB or network work), sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer` and answers `303` with a relative `Location` `/ledger/bank-connections/result?bank=connected` or `?bank=failed&reason=<denied|bank_error|invalid_state|missing_code|restricted|failed|disabled>`. Order: disabled, state, consume, ledger module enabled for that user, bank `error` (`access_denied` is `denied`), missing `code`, `POST /sessions`. `code`, `state`, `error_description` and session data never reach a log line, error text or the redirect. Residual risks (accepted with D7): the state is not bound to the browser that started the flow, so finishing a consent that someone else started from their own session attaches that bank session to their user (restricted mode and a single-owner install make this unlikely); and a reverse proxy's access log contains `code` and `state` (single use, 15 minute TTL).
- **Connections:** one `bconn/{id}` per user and bank. The session ID is stored as `EncryptedSessionID` (`json:"-"`, separate `storableLedgerBankConnection` like the email account) and decrypted only to close or check the session. Re-authorizing replaces the record in place (same ID), carries accounts over by identification hash, then IBAN (mappings and last-sync fields kept, the balance status reset, `balancesRequested` set), resets `lostAt` and `notifiedDays` and deletes the old remote session best effort. `BankConnectionStatus`: `expired` (`lostAt` set or past `validUntil`), `expiring` (less than 14 days left), else `active`; an expired or lost consent is never used. Disconnect closes the remote session best effort (`remoteClosed`), deletes the record regardless and keeps imported transactions.
- **Mapping:** explicit `ledgerAccountId` per bank account, set at connect time and lazily (on `GET connections` and before each sync) when the IBAN matches a ledger account with the same currency that no other bank account uses, or by `PUT .../accounts/{uid}` (same currency, ledger IBAN empty or equal after `normalizeIBAN`, not used by another bank account; also changes an existing mapping, and a changed target resets the account's sync state so it syncs at the next tick). `DELETE .../accounts/{uid}` (`UnmapAccount`) clears the mapping and the sync state and sets `unmapped`, which keeps the IBAN auto-mapping away from the account until it is mapped by hand (the flag survives a re-authorization). Transactions already synced stay where they are. Only mapped accounts sync.
- **Sync:** `SyncConnection` (one per connection at a time, `ErrBankSyncRunning`; the manual endpoint uses a 15 minute context that is not cancelled with the client, `bankSyncAccountTimeout` 10 minutes per account). Window: the first sync of an account without transactions uses `strategy=longest`, later ones start at the newest stored booking date not after today minus 14 days (a future-dated row never becomes the anchor; with none the first-sync `longest` applies) (`BankSyncWindow`; `WRONG_TRANSACTIONS_PERIOD` is retried once with `longest`). All pages are fetched first (200 page cap, a repeated continuation key aborts), rows are converted (`BOOK` only, exact decimal amounts, sign from `credit_debit_indicator`, counterparty = the other side, non-EUR and invalid rows are counted and skipped), fingerprints are built (`eb1:` + SHA-256 over length-prefixed fields, see the design note) and the commit goes oldest first in chunks of 500 through `CommitLedgerSync`, which also does the ±2 day cross-source absorption (`idx/xdup/`, `idx/xabs/`) and upserts one batch record (`SourceType enablebanking`, empty filename, no file hash, only when something was imported). After a successful transaction sync of an account, `syncBalance` (`bank_balance.go`) fetches its balances and stores the booked one as a snapshot (`pickBookedBalance`: `ITBD`/`CLBD` only, EUR, newest date, `ITBD` first; see `docs/design/enablebanking/README.md`); it never fails the sync and records `lastBalanceStatus` `ok|unavailable|error` (`unavailable` = `IsBalanceAccessMissing` or no booked EUR balance), shown with `balancesRequested` of the connection (set for every consent stored since balances were requested, false for older ones) in the connection views. `Handler.afterImport` (suggestions, recurring detection) runs once per sync run that imported something. Per account status codes: `ok`, `unmapped`, `consent_expired`, `access_denied`, `account_not_accessible`, `rate_limited`, `bank_unavailable`, `app_error`, `timeout`, `error` (`classifyBankError`: session codes mark the consent lost and skip the rest of the connection; other 401/403 check `GET /sessions/{id}` first). A failing account never stops others. A re-authorization during a running sync is safe: the sync's state write is dropped when the stored session differs from the one it started with, so the old session's failure cannot mark the new consent as lost. `CommitLedgerSync` retries badger conflicts (the user may review the same transactions meanwhile). When the context ends mid-run the partial summary is returned with the error, `afterImport` still runs for imported rows and the manual endpoint answers 504 `sync_timeout`. Only counts, IDs, status and the upstream error code are logged; never remittance text, names, IBANs, amounts, URLs, codes or session IDs (`TestBankFlowLogsNoSecrets`).
- **Scheduler and mails:** `BankSyncScheduler` runs a pass at start and then every tick (`schedulerTickInterval`, hourly with interval 0): per user with the ledger module enabled it prunes expired states, syncs due accounts (by `LastSyncAttemptAt`, so failures keep the interval; skipped with interval 0) and sends the expiry reminder. Reminders at 14 and 3 days (`bankExpiryReminderDays`): one mail for the smallest due threshold, all due thresholds are marked, no retroactive mails, no SMTP (`Mailer.IsConfigured()` false) skips without marking, a send error is retried at the next tick. The mail names the bank, the end date and `PUBLIC_URL/ledger/bank-connections`, nothing else.

**Personal access tokens:** `internal/pat` stores revocable tokens for agents and scripts. Format `kpat_` + 32 random bytes (base64url); only the SHA-256 hash is stored (`pat_hash/{hash}` → user and token ID, plus the record `u/{userId}/pat/{id}`), the raw token is returned once on creation (`Cache-Control: no-store`). Scopes are `read`, `drafts`, `links` and `categorize` (`categorize` is the only scope whose MCP tools change entities directly, and it opens no REST route); at most 50 per user (409 above); optional expiry must lie in the future. `Store.Authenticate` returns `middleware.PATIdentity` or `middleware.ErrInvalidPAT` (unknown, revoked and expired alike) and updates `lastUsedAt` at most once a minute without ever resurrecting a revoked record. Tokens are outside the module prefixes and not exported. There is no account-deletion path today; a future one must delete `u/{userId}/pat/*` and the matching `pat_hash/{hash}` keys, which live outside the user prefix, so a prefix delete would leave orphaned hashes (they fail closed, but still leak hashes).

**MCP:** `POST /mcp` is a stateless streamable-HTTP MCP endpoint (`github.com/modelcontextprotocol/go-sdk` v1.8.0; `GET`/`DELETE` give 405). It sits on the outer mux next to `/api/v1/`, behind `middleware.Auth(PATOnly(), WithPATs, WithChallenge("Bearer"))` and the normal RequestID → Recovery → Metrics → Logging → CORS chain (`statusRecorder` implements `Unwrap`/`Flush` so SSE streaming works through the wrappers). Packages: `internal/mcptool` is the leaf framework (`Registrar`, `Spec{Name, Description, Scope, Module, ReadOnly}`, generic `Add[In, Out]`, `Call{UserID, TokenID, Scopes}` from the authenticated request and never from tool arguments, `ToolError` codes `insufficient_scope|module_disabled|not_found|invalid_input|already_pending|too_many_pending|paperless_not_configured|paperless_unavailable|public_url_not_configured|conflict|cancelled|internal_error`, `CreateDraft`, `CheckDate`/`CheckLen`); `internal/mcpserver` mounts the handler and holds the core tools (`list_modules` read, `search_paperless_documents` read, `attach_paperless_documents` links) and the server instructions; modules implement the optional `module.ToolProvider` (`RegisterTools(*mcptool.Registrar)`), which `module.Registry.RegisterTools` calls in registration order. `Handler` builds one `mcp.Server` per request (`Registrar.Build`, shared `SchemaCache`) because the SDK asks for the server several times per stateless request. A receiving middleware (the guard) filters `tools/list` to tools whose scope the token has and whose module is enabled and answers `tools/call` of anything else with a tool error (`insufficient_scope`, `module_disabled`, `IsError`), not a protocol error. Two transient failures are mapped in `mcptool.run` so agents know to repeat the call: exhausted conflict retries (`storage.ErrRetriesExhausted` from `storage.RetryConflicts`, or a raw `badger.ErrConflict`) become `conflict`, and a context error while the request context itself has ended becomes `cancelled`; a timeout of an upstream call inside a live request stays `internal_error`, and other `storage.ErrConflict` errors (duplicates) are not retryable. Both count as `tool_error` in the metrics. Other handler errors that are not a `ToolError` (and panics) are logged with tool name and token ID and returned as the fixed `internal_error`; arguments and results are never logged. A tool failure's text is `<code>: <message>`. Apart from the `categorize` tools, no tool writes entities. Draft tools never write entities: `CreateDraft` stores a pending draft with source `mcp`; an optional client `key` makes repeats `already_pending` while a draft exists (ref `k:<sha256(key)>`), without a key every call creates a new draft (ref `r:<uuid>`). Title, key and note are trimmed (a blank title or a non-empty blank key is `invalid_input`). A user can have about 500 pending MCP drafts (a soft cap: parallel calls can overshoot it by the number in flight) (`mcptool.DefaultMaxPendingDrafts`, counted in the same transaction as the create by `drafts.Store.CreateLimited`); parallel creates with the same key conflict in badger, so `CreateLimited` retries via `storage.RetryConflicts` and the loser gets `already_pending`; beyond that `CreateDraft` returns `too_many_pending` until the user decides some. Every tool sets `readOnlyHint` and `idempotentHint` and explicit `destructiveHint: false`, `openWorldHint: false` (`Spec.Idempotent` marks repeatable write tools). `attach_paperless_documents` derives the entity URL from `PUBLIC_URL` (`public_url_not_configured` when unset; there is no request-header fallback), checks that the entity exists for the user and that its module is enabled; `internal/server/mcp.go` finds the entity through the registry: each module that owns linkable entities implements the optional `module.EntityLocator` (`LocateEntity`: contract, purchase, vehicle, cost, transaction, with the UI path). `DisableLocalhostProtection` is on because requests carry a bearer token and a reverse proxy on the same host would otherwise be rejected. Config: `PUBLIC_URL` (absolute http(s) URL, trailing slash trimmed, no query/fragment; empty = unset). Metrics: `mcp_tool_calls_total{tool,outcome}` (`ok|tool_error|forbidden|internal_error`) and `mcp_tool_call_duration_seconds{tool}`.

**Logging:** `log/slog` — JSON handler in production, text in dev.

**Metrics:** Prometheus via `/metrics` endpoint. Tracks `mcp_tool_calls_total` (see MCP), `http_requests_total`, `http_request_duration_seconds`, `http_active_requests`, and for the LLM client `llm_requests_total{operation,outcome}`, `llm_request_duration_seconds{operation}`, `llm_tokens_total{operation,type}`, `llm_retries_total{operation}`.

**Middleware chain (outermost first):** RequestID → Recovery → Metrics → Logging → CORS → handler. Module routes additionally pass the enablement gate after auth.

**Auth:** JWT-based authentication. Registration and login seed default data for every enabled module (idempotent; re-enabling a module in settings re-seeds it). Stores accept `userID` as a parameter; handlers extract it from auth context. Passwords must be at least 8 characters and at most 72 bytes (bcrypt's limit; register and change, `checkNewPassword`). **Registration** (`config.Registration`, `core.Handler.SetRegistration`): `RegistrationFirstUser` (default) lets `POST /auth/register` create an account only while no user exists (`Store.HasUsers`; check and create run under `registerMu`, so two first registrations cannot both pass), `RegistrationOpen` always, `RegistrationClosed` never; refused with 403 `{"code":"registration_closed"}` before the body is read. The public `GET /api/v1/auth/config` (`{registrationOpen}`, `no-store`) lets the login page hide sign-up. **Sessions:** JWTs are HS256 `middleware.JWTClaims` (subject, 7 day expiry, `tv` = the user's `TokenVersion`, omitted for 0). `middleware.WithTokenVersions(coreStore)` compares `tv` with the stored version on every JWT request (one read; unknown user → 401, store error → 500), so tokens issued before the feature (no `tv`) keep working until the first password change. `PUT /settings/password` bumps `TokenVersion`, which ends every session of the user, and answers `200 {"token"}` with a token for the current one (the frontend stores it). Personal access tokens are not affected. `/auth/login` and `/auth/register` share a per-IP token-bucket rate limit (`internal/middleware/ratelimit.go`): `AUTH_RATE_LIMIT` requests (default 10) per `AUTH_RATE_WINDOW` (default `1m`), 0 disables; set `TRUST_PROXY=true` behind a reverse proxy so client IPs come from `X-Real-IP`/`X-Forwarded-For`.

**Personal access tokens in the API:** `middleware.Auth(secret, opts...)` accepts a JWT or a personal access token (`kpat_…`, `WithPATs(verifier)`); it puts a `middleware.Principal` (`UserID`, `Kind` `jwt|pat`, `TokenID`, `Scopes`) into the context (`GetPrincipal`, `IsPAT`, `HasScope`; `GetUserID` keeps working). Failures are an identical `401 {"error":"unauthorized"}` for unknown, revoked, expired and malformed tokens (a verifier error is `500`); options `PATOnly()` (reject JWTs) and `WithChallenge("Bearer")` (set `WWW-Authenticate`) are meant for `/mcp`. Tokens are never logged. Reach is an explicit table keyed by the registered mux pattern (`internal/server/scopes.go`, enforced by `middleware.ScopeGuard` around the API mux, JWT requests pass untouched, a pattern missing from the table is denied): `read` for every `GET` (including the exports), `drafts` for `PUT /drafts/{id}` and the single draft accept/reject (the batch accept `POST /drafts/accept-batch` is `denied`, because it creates entities from draft input and a `drafts` token could otherwise turn its own MCP drafts into entities without review), `links` for `POST /paperless/links/{entityType}/{entityId}` and `POST /ledger/transactions/{id}/references`, `denied` (never reachable with a token) for every other mutation, `jwt-only` for `/tokens*`, `PUT /settings/password` and `GET /ledger/bank/aspsps` (the bank list spends Enable Banking quota; the other bank mutations, including sync, are `denied`, `GET /ledger/bank/connections` is `read`; the public callback has no entry) (`/auth/*` is public and outside the API mux). A rejected request gets `403 {"error":"insufficient scope","code":"insufficient_scope"}`; 404/405 are answered by the mux as usual and module gating still applies afterwards. A new route must get a table entry: `TestRouteRulesCoverRoutes` builds the real app (`buildApp`) and fails for missing or stale entries. **Accepted residual risk (decided with the user, not changed):** over the REST API the scopes are broader than the MCP tools. A `drafts` token can accept drafts, including with an unverified `entityId` (accept does not check that the entity exists), so an agent can clear its own drafts from the inbox without the user reviewing them; for **paperless-sourced** drafts, accepting also stores a paperless link for the unchecked entity, writes the request's `entityUrl` into the document's "Kontor" custom field and swaps the inbox tag for the done tag in paperless, and rejecting removes the inbox tag; for **email-sourced** drafts, accepting stores an email link for the unchecked entity and both decisions mark the message as done locally, and when the account has `draftsProcessedAction` `move` or `delete` either decision moves or deletes that message in the mailbox (accepted by the user with Kontor#48: a `drafts` token can thereby empty the drafts folder into the target folder or the trash, limited to messages that have a pending draft); `PUT /drafts/{id}` can edit the input of any pending draft; and a `links` token chooses the `entityUrl` that is written into the user's paperless "Kontor" custom field and skips the entity-exists check of `POST /paperless/links/{entityType}/{entityId}`. The MCP tools do not have these gaps: `attach_paperless_documents` derives the URL from `PUBLIC_URL` and verifies the entity, and there is no MCP tool to accept drafts. Give tokens only the scopes a client needs, and REST access only to clients you trust with these.

- `internal/enablebanking/` — Enable Banking API client (RS256 JWT, consent, sessions, transactions, error classification); `enablebankingtest/` is the fake API server for tests
- `internal/cryptoutil/` — AES-GCM string encryption (email passwords, paperless tokens, bank sessions), keyed by `ENCRYPTION_KEY` (32 bytes raw or base64; the deprecated `EMAIL_ENCRYPTION_KEY` is used when it is unset, with a startup warning, and startup fails when both are set to different values)
- `internal/paperless/` — Optional paperless-ngx integration: per-user config (encrypted API token) and pipeline settings, outbound HTTP client (search, thumbnails, custom-field back-links, tags, document content, bulk tag edits); it does not follow redirects (a 3xx is a `StatusError`), reads JSON responses up to 16 MiB and thumbnails up to 5 MiB (`ErrResponseTooLarge`), and its errors have fixed texts (`StatusError` "paperless answered HTTP n", `ErrUnreachable`, `ErrInvalidResponse`; `Cause` gives the underlying error for the log, `PublicError` the client text, 401/403 = "paperless rejected the API token"), so upstream bodies and dial errors never reach a response or warning; the base URL must not carry a query, fragment or user info, central document-link store, `Service` (shared client resolution, attach/detach with done tag), handlers, the draft pipeline (`pipeline.go`) and its draft hooks; `paperlesstest/` holds a fake paperless API for tests. Routes are ungated (not module-scoped); handlers return 409 when the user has not configured the integration. Deleting an entity leaves its paperless links as unreachable keys (accepted; no sweep yet)
- `internal/mcptool/` — MCP tool framework (registrar, per-request server with scope/module guard, error mapping, metrics, draft helper); leaf package imported by modules
- `internal/mcptool/mcptooltest/` — Test helper: registrar plus in-memory MCP client for module tool tests
