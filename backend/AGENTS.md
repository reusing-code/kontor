# AGENTS.md

This file provides guidance to AI coding agents when working with code in this repository.

## Documentation maintenance

After every change, check whether `AGENTS.md` (root, `backend/`, `frontend/`) and `README.md` (root, `frontend/`) need updating. Keep these files in sync with the actual code — new modules, routes, DB keys, API endpoints, and dependency versions must be reflected here.

## Prerequisites

- **Go 1.27+** — https://go.dev/dl/
- **Task** — Task runner (taskfile.dev): `go install github.com/go-task/task/v3/cmd/task@latest` or `pacman -S go-task`
- **Air** — Live reload for Go: `go install github.com/air-verse/air@latest`
- **golangci-lint** (optional) — Linter: `go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0` or `pacman -S golangci-lint`; use the version CI pins in the root `.tool-versions` (`task lint` warns on a mismatch)

## Commands

- `task dev` — Start with Air (live reload), sets `CORS_ORIGIN` for frontend dev server
- `task clean-db` — Delete the local dev database (`./data`)
- `task build` — Build the binary
- `task test` — Run tests
- `task lint` — Run golangci-lint (warns if the installed version differs from `.tool-versions`)

## Architecture

Go 1.27+ stdlib `net/http` with method+pattern routing. Single binary that optionally serves the frontend SPA.

**Modules:** Each feature module implements the `module.Module` interface (`internal/module`): `ID`, `Prefix` (its DB key prefix), `Migrations`, `RegisterRoutes`, `Seed`, `StartBackground`, `IsEmpty`, `ExportSection`, `ImportSection`, `PruneDeadLinks`. The server builds all modules, registers them in a `module.Registry` (order matters — it is also the import order), runs their migrations, and registers their routes through `module.Router`, which wraps every handler in the enablement gate. Users can disable modules in settings (`disabledModules`, stored as the disabled set so everything defaults to enabled); gated routes return `403 {"code":"module_disabled"}`. Data of disabled modules is kept.

**Cross-module links:** Ledger transactions reference contract/purchase/vehicle/cost items (`link.RefContract|RefPurchase|RefVehicle|RefCost`), and those items track linked transaction IDs (`linkedTransactionIds`). The synchronization goes through `internal/storage/link.Registry` inside a single badger transaction: contracts/purchases/auto stores implement `link.Target` (AddLink/RemoveLink/Exists; the auto store is the vehicle target and registers a small `costLinks` adapter for cost entries), the ledger store implements `link.TransactionSide`. Deleting an item strips the references to it from its transactions (deleting a vehicle does so for the vehicle and each of its cost entries); updating an item through its module endpoint keeps its links. Modules never import each other; wiring happens in `internal/server`.

**Storage:** BadgerDB (embedded LSM-tree KV store) behind `storage.Engine` (`internal/storage`), shared by per-module stores. Data is stored as JSON documents; every module's data lives under `u/{userId}/mod/{moduleId}/...` (see the root `AGENTS.md` for the full key schema). Sentinel errors (`ErrNotFound`, `ErrConflict`, ledger-specific ones) live in `internal/storage`.

**Migrations:** Per module (`internal/storage/migration`): `migration.RunModule` applies a module's pending migrations against its own `_meta/schema/{moduleId}` version key at startup. A module's migrations must only touch keys under its own prefix.

**Export/import:** Versioned envelope (`{"format":"kontor-export","formatVersion":2,...}`) with one section per module, each stamped with the module's section schema version. Full and per-module endpoints; import requires the affected modules to be empty and enabled, preserves IDs verbatim, strips ledger references to items that were not imported, and prunes dead transaction links (with warnings). Orchestrated in `internal/core/export.go`; each module owns its section shape.

**Backups:** Optional periodic full BadgerDB snapshots (`internal/storage/backup.go`) to `BACKUP_DIR` every `BACKUP_INTERVAL` (default `24h`), keeping the `BACKUP_KEEP` newest files (default 7). Empty `BACKUP_DIR` disables. Restore snapshots with the `badger` CLI (`badger restore`) or `badger.DB.Load`.

**Config:** Environment variables via `caarlos0/env` struct tags. See `.env.example` for all options.

**Bank import config:** `ENABLE_BANKING_APP_ID` and `ENABLE_BANKING_KEY_PATH` (RSA private key, PEM, PKCS#1 or PKCS#8) enable the Enable Banking import; `ENABLE_BANKING_API_URL` (default `https://api.enablebanking.com`, for tests and sandboxes) and `ENABLE_BANKING_SYNC_INTERVAL` (default `24h`; `0` disables only the automatic sync, the scheduler still sends expiry mails and prunes states). Startup fails when only one of id/key is set, when enabled without a valid `ENCRYPTION_KEY`, for an invalid URL or negative interval, and in `buildApp` when the key file is unreadable or not RSA. Without id and key the feature is off (info log `bank import disabled`). Enabled without `PUBLIC_URL` logs a warning and consent requests answer 409 `public_url_not_configured`. The key, JWTs and session IDs are never logged.

**LLM:** Optional server-wide OpenAI-compatible endpoint (`internal/llm`). `LLM_BASE_URL` (unset disables), `LLM_MODEL` (required once the base URL is set), `LLM_API_KEY` (optional bearer token), `LLM_TIMEOUT` (per attempt, default `60s`), `LLM_VISION_MODEL` (optional; model for requests with images on the same endpoint, capability `llmVision`); partial config fails at startup. `llm.New` returns a `*llm.Client` or `llm.Disabled`; both implement `llm.Extractor` (`Extract`, `Enabled`). Requests go to `POST {base}/chat/completions` with `response_format: json_schema` (`strict: true`); schemas come from `llm.SchemaFor[T]` (every field required, only pointer fields nullable, so unknown text comes back as `""`; nullable objects and enums use `anyOf`; optional `llm:"desc=...,enum=a|b"` tag. Anthropic models allow at most 16 nullable fields per schema). Output that is not a JSON object or does not decode into `T` (`llm.ExtractAs`) is retried once; A request with `Request.Images` (`llm.Image{MediaType, Data}`) is sent to the vision model with the user message as a parts array (one `text` part when the input is non-empty, one `image_url` data URL per image); without a vision model it fails with `ErrVisionDisabled` before any call. Text requests keep the plain string content and the normal model. Errors are `ErrDisabled`, `ErrInvalidOutput`, `ErrRefused`, `ErrTruncated` (no retry) and `*APIError` (upstream `error.message` only). Never log prompts or model output or put them into errors. Tests use `llmtest.Fake`.

**Drafts:** `internal/drafts` is the source-agnostic draft inbox (model, store, handler). A draft has `status` (`pending|accepted|rejected`), `targetType` (`purchase|contract|cost|vehicle|contract_category|purchase_category|ledger_category|ledger_account|none`), `parentId` (category for purchase/contract, vehicle for cost, optional parent category for `ledger_category`; rejected with 400 for vehicle, contract/purchase category and ledger account), `input` (the module's create-input JSON), `source{kind,ref,title,url}` (kind `paperless|ledger|mcp`, `email|text` reserved), `note` (code the UI translates: `unclassified`, `empty_content`, `llm_invalid_output`, `llm_refused`, `llm_truncated`, `llm_request_rejected`, `currency_converted`, `currency_not_converted`, `recurring_payment`, `recurring_payment_ended`), `result{entityType,entityId}`. `Store.Create` fails with `ErrDuplicateSource` while a draft for the same source exists; `Decide` frees the source. Sources register `SourceHooks` on the handler: `OnAccept` runs before the draft is marked accepted (error → 500, draft stays pending), `OnReject` after. The accept `entityType` must equal the draft's `targetType` (any type but `none`). `Store.Counts` backs `GET /drafts/summary`. The classifier (`extraction.Targets`) is unchanged and never proposes the new types. Accept does not verify that the entity exists.

**Extraction:** `internal/extraction` is the shared classifier. `Classifier.EnabledTargets` / `LoadCatalog` build what the model may choose from (enabled purchase/contract/cost targets, categories and vehicles with IDs; module lookups through `extraction.Deps`, wired in `internal/server/extraction.go`, so the package does not import modules); `Catalog.Only(target)` forces one type. `Classify(ctx, operation, catalog, Input{Kind: InputDocument|InputNote, Title, Text}, now)` makes one `llm.ExtractAs` call (schema `{kind, confident, purchase?, contract?, cost?}`, each extract with `currency`; prompt per input kind with today's date; text truncated to 20k characters) and returns a `Proposal{Target, ParentID, Input, Note, Confident, Currency}` whose input has the module create-input shape. Unknown category/vehicle IDs, invalid dates, intervals, URLs and cost types are dropped or defaulted. `none`, empty text and `ErrInvalidOutput`/`ErrRefused`/`ErrTruncated`/LLM 400/413/422 give a `none` proposal with a note; other LLM errors are returned (transient; `IsTimeout` for timeouts). `Confident` is the model's flag and false without a valid parent or with a foreign currency. Non-EUR amounts are converted with `fx.Rates` at the purchase/cost date (today if missing, contracts always today), rounded to cents, original appended to `comments` (`USD 640.00 → EUR 572.86 (ECB 2026-10-30, 1 USD = 0.89509 EUR)`), note `currency_converted`; without a rate (disabled, unknown code, lookup failure) the amount is dropped, comment `USD 640.00 (not converted)`, note `currency_not_converted`.

**FX rates:** `internal/fx` looks up ECB reference rates from a Frankfurter-compatible API: `GET {FX_RATES_URL}/{date}?base={from}&symbols={to}` (default `https://api.frankfurter.dev/v1`; `off` disables, an empty value falls back to the default). Future dates are clamped to today; past-date rates are cached in memory; 10s timeout. `fx.Disabled` returns `ErrDisabled`. Consumers: the shared classifier (to EUR) and the ledger email-order matching (order currency to the transaction's currency); the server builds one instance for both.

**Quick add:** `internal/quickadd` handles `POST /api/v1/quick-add` with the classifier (operation `quickadd.classify`, note prompt). Stateless; the typed text is never logged. The same route accepts `multipart/form-data` (`upload.go`): `file` (required, at most `MaxFileBytes` = 10 MiB), optional `text` (a hint, same 2000 character cap) and `targetType`; unknown or repeated fields are a 400. The file type is sniffed from the bytes (`http.DetectContentType`), the client's content type and file name are ignored and never used. An image (JPEG, PNG, WebP) becomes `extraction.Input{Kind: InputUpload, Images}` with operation `quickadd.classify_image` and needs the vision model (the handler gets `vision` from `Config.LLMVisionEnabled()`). A PDF is read by `pdfText` (`pdftext.go`, on `github.com/ledongthuc/pdf`, pure Go): its own content-stream walk over at most 30 pages, 2 million operators and 100 kB of text, which inserts spaces from `TJ` gaps and from `Td` moves along a line measured against the font's glyph widths (kerning inside a word must not split it, a jump to a right-aligned amount must); parser panics are recovered. The text goes through the normal model as `InputUpload` (operation `quickadd.classify`); there is no OCR, so fewer than 20 letters or digits is `pdf_no_text`. Coded failures are `{"error","code"}`: 413 `file_too_large`, 415 `unsupported_file`, 409 `vision_not_configured`, 422 `pdf_no_text`, 422 `file_unreadable` (broken or encrypted PDF). Only the kind (`text|image|pdf`) and byte size of a request are logged, never the file name, content or extracted text (`TestUpload_LogsNoContent`). Known limit: the PDF parser inflates streams without a size cap, so a crafted PDF can cost CPU and memory; the route is JWT-only (`denied` for tokens).

**Paperless pipeline:** `paperless.Pipeline` (`PAPERLESS_PIPELINE_INTERVAL`, default `15m`, `0` disables; not started when the LLM is disabled). Per user with the pipeline enabled, paperless configured and at least one of purchases/contracts/auto enabled: find the inbox tag (never created by the pipeline), list tagged documents (oldest first, up to 500), skip documents that have a draft, fetch content for at most 10 new ones and classify each with the shared classifier (operation `paperless.classify`, document prompt; see Extraction). `none` proposals become `none` drafts with a note; transient LLM errors create no draft, stop the pass and are retried next time. `NewPipeline` takes the classifier and a user-ID lister (wired in `internal/server`). `paperless.Service` resolves a user's client and implements attach (links, back-link, done tag, optional tag removal) and detach (clears back-link, removes the done tag with the last link); `paperless.DraftHooks` uses it for accept (link must be stored, the rest is best effort → warnings) and reject (remove inbox tag). Tests use `paperless/paperlesstest` (fake paperless API) and `llmtest.Fake`.

**Email order extraction:** `ledger.EmailService` (`email_service.go`, `email_pipeline.go`, `email_extract.go`, `email_preclass.go`, `email_match.go`) turns messages into `LedgerEmailOrder`s with `llm.Extractor` (injected through `ledger.Config.Extractor`, nil = disabled). One shared path (`processMessages`) serves IMAP scans and `.eml` uploads: the IMAP scan selects the account's `folder` (required; modified UTF-7 encoded), fetches only headers (`BODY.PEEK[HEADER]`) of the newest 250 messages since `max(scanSince, lastScanAt−48h)` and downloads a message only when it needs extraction. Dedup runs before any LLM call: the key is the Message-ID (`mid:<hash>` when it is longer than 200 bytes or has control characters, `nomid:<hash>` without one); a message with an order (`idx/eord_msgid`) or a processed marker (`idx/eseen` with a reason: `not_order` for `isOrder=false`, `preclass` for pre-classified non-orders, `too_large` above 25 MB, `unreadable`, `unusable`) is skipped. `extractOrder` sends sender, subject, date and the text body (cap 12 000 characters) with the system prompt that treats the email as untrusted data; `validateExtraction` checks total, currency, date (falls back to the Date header), payment method enum, items. Failures: `llm.ErrDisabled` → `ErrEmailLLMDisabled` before anything is downloaded (409, scheduler status "skipped"); invalid/refused/truncated output (`isUnusableLLMOutput`) and a result that fails validation → per-message warning, no marker, retried next scan, and counted in `idx/efail/{accountId}/{dedupKey}` (`handleFailedExtraction`): at `LEDGER_EMAIL_MAX_EXTRACTION_FAILURES` (default 3, at least 1; `ledger.Config.EmailMaxExtractionFailures`) the message is marked `unusable` with one warning ("ignored from now on") instead and later scans skip it without an LLM call; the counter is deleted in the transaction that stores the order or sets any processed marker (`CreateScannedLedgerEmailOrder`, `MarkLedgerEmailsSeen`) and with the account, uploads count like scans; a rejected request (non-transient 4xx such as 400, 404, 422) → warning "LLM request was rejected", no marker, not counted (it may be a configuration error such as a wrong model name), retried at every scan inside the lookback window; transient errors → warning and `skipped`, not counted, three in a row stop the scan as `partial`; IMAP I/O errors abort the scan (the connection is unusable), a tagged `NO` on a fetch only skips the message and makes the scan incomplete, but after 3 refusals of the same message (counted in `idx/erej/{accountId}/{key}`, `uid:N` for header fetches) it is marked `unreadable` and ignored; context end stops the scan and keeps stored orders. Warnings and logs contain only message labels (`uid N`, file names) and fixed texts, never email content or model output. `deriveMatchRule` (pure) gives the counterparty pattern and charge window from merchant and payment method (PayPal `paypal` −3/+7; merchant containing `amazon` without PayPal `amazon` −3/+60; otherwise the quoted merchant −3/+30; a merchant shorter than 3 characters or none → no auto-link); `matchRuleForOrder` keeps legacy importer orders unchanged. Amounts are compared per transaction currency (`autoLinkOrder`): transactions in the order's currency must match exactly (alone or as a split payment of up to 4); only when none does, transactions in another currency (a USD order paid from an EUR account) are compared with the order total converted by `fx.Rates` (`ledger.Config.Rates`, nil = disabled) at the order date, and exactly one within ±5 % (`fxToleranceBasisPoints`, conversion fees and rate drift) is linked with the warning `linked by converted amount`; several give `multiple converted transaction matches` and no link, and converted amounts are never combined into split payments. Without a rate (FX off, unknown currency, lookup failure) the order is stored unmatched without a warning and is not retried. Stored orders always keep the extracted currency and total; all currencies are treated as two-decimal minor units. New orders have `importerId: "llm"`. Optional per-account `preClassify` first sends sender and subject of batches of 40 (fail open: anything the model does not clearly reject is extracted). One scan per account at a time; `LastScanAt` (the lookback anchor) only advances after a complete IMAP scan (no `partial`, no `skipped`); `LastScanAttemptAt` is stamped by every attempted scan and schedules the next background scan, so failed or incomplete accounts keep the normal interval while accounts skipped for a missing folder/LLM stay due each tick. Scan state is written with `SetLedgerEmailAccountScanState`, which changes only the scan fields, so edits made during a scan are kept (and account edits go through `ModifyLedgerEmailAccount`, one load-modify-store transaction); changing host, port, username, TLS, folder or the password clears `LastScanAttemptAt` so the next tick rescans; racing transactions are retried on `badger.ErrConflict`; uploads never move `LastScanAt`. Tests use `llmtest.Fake` and the fixtures in `docs/design/email/`.

**Category suggestions:** `ledger.CategorySuggester` (`categorization_llm.go`, `store_suggestion.go`, `handler_suggestions.go`) proposes ledger categories with `llm.ExtractAs` (operation `ledger.category_suggest`, same `ledger.Config.Extractor`). A candidate is `needsReview`, uncategorized, without special category or transfer pair, with counterparty or purpose. A run first re-applies `MatchFields` with the current categories: a match sets the category with source `keyword` (still `needsReview`) and is never sent. Candidates with a stored suggestion are skipped, except when its category was deleted, or when it is a marker without category (model found nothing) and a category was created or updated after it. Candidates go newest first, `LEDGER_SUGGEST_BATCH_SIZE` per call (default 25, 1..100) and at most `LEDGER_SUGGEST_MAX_PER_RUN` per run (default 100, ≥ batch size; invalid values fail at startup); `remaining` reports the rest. Input: numbered category paths, examples (reviewed transactions whose counterparty shares a word of at least 3 characters, no stop words or numbers; 3 per transaction, 30 per batch), and numbered transactions (booking date, amount + currency, counterparty 200 / purpose 300 runes). Output `{index, categoryNumber (0 = none), confidence high|medium|low, matchWord}`: out-of-range or duplicate indexes are dropped, an unknown category becomes a marker; a match word is kept only when it is 3..64 runes, has no comma, is not only digits, is a case-insensitive substring of the transaction's counterparty/purpose (so the rule catches it), is not a match word already and is not proposed for two categories in one batch. Storage `sug/{txnId}`; `PutLedgerCategorySuggestions` and `ApplyLedgerRuleMatches` re-check the candidate state inside the write transaction; `ReviewLedgerTransaction` deletes the suggestion; the review queue only shows suggestions of candidates whose category exists. Errors: `ErrDisabled` → `ErrSuggestLLMDisabled` (409); invalid/refused/truncated output and 4xx → warning, the batch is retried next run; transient errors and context end → `partial`, the run stops and keeps what it stored. One run per user (`ErrSuggestRunning`, 409); `RunInBackground` is called after every successful import commit (no-op without LLM or while a run is going), bounded by the module's background context and a 5 minute timeout like the manual run (which is not cancelled when the client disconnects). Logs carry counts only.

**Recurring payments:** `ledger.DetectRecurring` (`recurring.go`, pure) finds recurring outgoing payments; `ledger.RecurringService` (`recurring_service.go`, `store_recurring.go`, `handler_recurring.go`) proposes them as `contract` drafts (source kind `ledger`). Candidates: negative amount, currency `EUR` (case-insensitive; an empty currency is skipped, the importers always set one), no internal transfer or transfer pair. Counterparty key: `counterpartyTokens` of the name joined with spaces, else `iban:` + the upper-cased IBAN without spaces, else skipped. Per key, in booking-date order (ties by ID), a payment joins the first chain whose last amount is within max(10 %, 100 cents) of it, otherwise it starts a new chain (splits PayPal-like counterparties by amount, keeps gradual price increases together). The median gap in days picks the interval: monthly 26–35 (≥ 3 payments), quarterly 80–100 (≥ 3), yearly 350–380 (≥ 2); at least 80 % of the gaps must lie in that window (so one missed month needs at least 5 other regular gaps). A chain containing a transaction already linked to a contract is dropped, so an accepted group is not proposed again when new payments arrive. A group carries the latest counterparty name (IBAN fallback), interval, the latest amount as price, first and last booking date, `ended` (last payment older than today − 2 intervals) and the transaction IDs; `ref = hex(sha256(key|interval|firstTxnID))[:32]`, stable while the series grows. A run (`RunUser`, one per user, `ErrRecurringRunning` → 409; `ErrTargetModuleDisabled` → 403 `module_disabled` while contracts is disabled; without a draft store 409) skips groups with a pending draft (`HasSource`) or a `rejected` record, writes `recur/{ref}` (`{transactionIds, status: pending, createdAt}`) and then the draft: input `{name, company, price, billingInterval, startDate, endDate?}` (`endDate` = last payment when ended), no parent (the user picks the category in the inbox), title `<name> · <n>× <amount> EUR`, no URL, note `recurring_payment` or `recurring_payment_ended`. At most 20 new drafts per run and 50 pending ledger drafts (`CreateLimited`; the run stops at the cap). A pending record without a draft (the create failed) is overwritten by the next run. `RunInBackground` runs after every successful import commit (no-op while a run is going), bounded by the module's background context and a 2 minute timeout like the manual run. Hooks (`RecurringDraftHooks`, `(*Module).DraftHooks()`, registered in `internal/server`): accept checks that contracts is enabled, links all recorded transactions to the new contract in one badger transaction (`LinkLedgerTransactionsToTarget`; an unknown contract → error, the draft stays pending; missing transactions → a warning with their count) and deletes the record; without a record it only warns. Reject sets the record to `rejected` (creating it if missing). Logs carry counts only.

**Bank import:** `internal/enablebanking` is the HTTP client: RS256 application JWT (`kid` = app ID, `iss enablebanking.com`, `aud api.enablebanking.com`, one hour, cached until 5 minutes before expiry, clock injectable), `ASPSPs`, `StartAuth`, `CreateSession`, `SessionStatus`, `DeleteSession`, `Transactions`; responses are read through a 10 MiB limit, 30 s default timeout, no retries. Errors never carry upstream message text, URLs or key material: `APIError{Status, Code}` keeps only the upstream `error` code if it matches `^[A-Z_]{1,64}$`, `TransportError` keeps only the cause of the `url.Error` (the URL contains session IDs and account UIDs); classifiers `IsRateLimited`, `IsSessionUnusable`, `IsAccountNotAccessible`, `IsAppAuth`, `IsWrongTransactionsPeriod`, `IsUnavailable`. `enablebankingtest.New(t)` is the in-memory fake API (JWT verification on every request, `AllowCode`, `SetTransactions`, `SetPageSize`, `FailNext`/`FailAlways`/`FailTransactionRequest`, recorders for auth requests, session calls and transaction queries). The ledger side (`ledger.BankService`, `bank_service.go`, `bank_sync.go`, `bank_scheduler.go`, `bank_notify.go`, `bank_convert.go`, `bank_window.go`, `store_bank.go`, `handler_bank.go`) works like this:
- **Consent:** `StartAuthorization` checks `PUBLIC_URL` and the bank (`GET /aspsps?country=<CC>&psu_type=personal&service=AIS`, cached 10 minutes per country; `verified` = name contains `dkb` or `comdirect`), stores a single-use state and posts `/auth` with `valid_until = now + min(maximum_consent_validity, 180 days) − 5 min` (90 days without a maximum), `transactions` and `transactions_extended_history` access, `psu_type personal` and the redirect URL `PUBLIC_URL/api/v1/ledger/bank/callback`. The state is `base64url(AES-GCM(userID + "." + 128 random bits))`: unforgeable without `ENCRYPTION_KEY`, no global index, nothing about the user reaches the bank. `bstate/{sha256(state)}` is consumed in one badger transaction (unknown, used or expired state = `ErrBankStateInvalid`, TTL 15 minutes).
- **Callback (public):** `GET /api/v1/ledger/bank/callback` is registered on the outer mux, not in the scope table. It never reads `Authorization`, is not rate limited (a forged state fails at AES-GCM before any DB or network work), sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer` and answers `303` with a relative `Location` `/ledger/bank-connections/result?bank=connected` or `?bank=failed&reason=<denied|bank_error|invalid_state|missing_code|restricted|failed|disabled>`. Order: disabled, state, consume, ledger module enabled for that user, bank `error` (`access_denied` is `denied`), missing `code`, `POST /sessions`. `code`, `state`, `error_description` and session data never reach a log line, error text or the redirect. Residual risks (accepted with D7): the state is not bound to the browser that started the flow, so finishing a consent that someone else started from their own session attaches that bank session to their user (restricted mode and a single-owner install make this unlikely); and a reverse proxy's access log contains `code` and `state` (single use, 15 minute TTL).
- **Connections:** one `bconn/{id}` per user and bank. The session ID is stored as `EncryptedSessionID` (`json:"-"`, separate `storableLedgerBankConnection` like the email account) and decrypted only to close or check the session. Re-authorizing replaces the record in place (same ID), carries accounts over by identification hash, then IBAN (mappings and last-sync fields kept), resets `lostAt` and `notifiedDays` and deletes the old remote session best effort. `BankConnectionStatus`: `expired` (`lostAt` set or past `validUntil`), `expiring` (less than 14 days left), else `active`; an expired or lost consent is never used. Disconnect closes the remote session best effort (`remoteClosed`), deletes the record regardless and keeps imported transactions.
- **Mapping:** explicit `ledgerAccountId` per bank account, set at connect time and lazily (on `GET connections` and before each sync) when the IBAN matches a ledger account with the same currency that no other bank account uses, or by `PUT .../accounts/{uid}` (same currency, ledger IBAN empty or equal after `normalizeIBAN`, not used by another bank account). Only mapped accounts sync.
- **Sync:** `SyncConnection` (one per connection at a time, `ErrBankSyncRunning`; the manual endpoint uses a 15 minute context that is not cancelled with the client, `bankSyncAccountTimeout` 10 minutes per account). Window: the first sync of an account without transactions uses `strategy=longest`, later ones start at the newest stored booking date not after today minus 14 days (a future-dated row never becomes the anchor; with none the first-sync `longest` applies) (`BankSyncWindow`; `WRONG_TRANSACTIONS_PERIOD` is retried once with `longest`). All pages are fetched first (200 page cap, a repeated continuation key aborts), rows are converted (`BOOK` only, exact decimal amounts, sign from `credit_debit_indicator`, counterparty = the other side, non-EUR and invalid rows are counted and skipped), fingerprints are built (`eb1:` + SHA-256 over length-prefixed fields, see the design note) and the commit goes oldest first in chunks of 500 through `CommitLedgerSync`, which also does the ±2 day cross-source absorption (`idx/xdup/`, `idx/xabs/`) and upserts one batch record (`SourceType enablebanking`, empty filename, no file hash, only when something was imported). `Handler.afterImport` (suggestions, recurring detection) runs once per sync run that imported something. Per account status codes: `ok`, `unmapped`, `consent_expired`, `access_denied`, `account_not_accessible`, `rate_limited`, `bank_unavailable`, `app_error`, `timeout`, `error` (`classifyBankError`: session codes mark the consent lost and skip the rest of the connection; other 401/403 check `GET /sessions/{id}` first). A failing account never stops others. A re-authorization during a running sync is safe: the sync's state write is dropped when the stored session differs from the one it started with, so the old session's failure cannot mark the new consent as lost. `CommitLedgerSync` retries badger conflicts (the user may review the same transactions meanwhile). When the context ends mid-run the partial summary is returned with the error, `afterImport` still runs for imported rows and the manual endpoint answers 504 `sync_timeout`. Only counts, IDs, status and the upstream error code are logged; never remittance text, names, IBANs, amounts, URLs, codes or session IDs (`TestBankFlowLogsNoSecrets`).
- **Scheduler and mails:** `BankSyncScheduler` runs a pass at start and then every tick (`schedulerTickInterval`, hourly with interval 0): per user with the ledger module enabled it prunes expired states, syncs due accounts (by `LastSyncAttemptAt`, so failures keep the interval; skipped with interval 0) and sends the expiry reminder. Reminders at 14 and 3 days (`bankExpiryReminderDays`): one mail for the smallest due threshold, all due thresholds are marked, no retroactive mails, no SMTP (`Mailer.IsConfigured()` false) skips without marking, a send error is retried at the next tick. The mail names the bank, the end date and `PUBLIC_URL/ledger/bank-connections`, nothing else.

**Personal access tokens:** `internal/pat` stores revocable tokens for agents and scripts. Format `kpat_` + 32 random bytes (base64url); only the SHA-256 hash is stored (`pat_hash/{hash}` → user and token ID, plus the record `u/{userId}/pat/{id}`), the raw token is returned once on creation (`Cache-Control: no-store`). Scopes are `read`, `drafts` and `links` (no write scope); at most 50 per user (409 above); optional expiry must lie in the future. `Store.Authenticate` returns `middleware.PATIdentity` or `middleware.ErrInvalidPAT` (unknown, revoked and expired alike) and updates `lastUsedAt` at most once a minute without ever resurrecting a revoked record. Tokens are outside the module prefixes and not exported. There is no account-deletion path today; a future one must delete `u/{userId}/pat/*` and the matching `pat_hash/{hash}` keys, which live outside the user prefix, so a prefix delete would leave orphaned hashes (they fail closed, but still leak hashes).

**MCP:** `POST /mcp` is a stateless streamable-HTTP MCP endpoint (`github.com/modelcontextprotocol/go-sdk` v1.8.0; `GET`/`DELETE` give 405). It sits on the outer mux next to `/api/v1/`, behind `middleware.Auth(PATOnly(), WithPATs, WithChallenge("Bearer"))` and the normal RequestID → Recovery → Metrics → Logging → CORS chain (`statusRecorder` implements `Unwrap`/`Flush` so SSE streaming works through the wrappers). Packages: `internal/mcptool` is the leaf framework (`Registrar`, `Spec{Name, Description, Scope, Module, ReadOnly}`, generic `Add[In, Out]`, `Call{UserID, TokenID, Scopes}` from the authenticated request and never from tool arguments, `ToolError` codes `insufficient_scope|module_disabled|not_found|invalid_input|already_pending|too_many_pending|paperless_not_configured|paperless_unavailable|public_url_not_configured|internal_error`, `CreateDraft`, `CheckDate`/`CheckLen`); `internal/mcpserver` mounts the handler and holds the core tools (`list_modules` read, `search_paperless_documents` read, `attach_paperless_documents` links) and the server instructions; modules implement the optional `module.ToolProvider` (`RegisterTools(*mcptool.Registrar)`), which `module.Registry.RegisterTools` calls in registration order. `Handler` builds one `mcp.Server` per request (`Registrar.Build`, shared `SchemaCache`) because the SDK asks for the server several times per stateless request. A receiving middleware (the guard) filters `tools/list` to tools whose scope the token has and whose module is enabled and answers `tools/call` of anything else with a tool error (`insufficient_scope`, `module_disabled`, `IsError`), not a protocol error. Handler errors that are not a `ToolError` (and panics) are logged with tool name and token ID and returned as the fixed `internal_error`; arguments and results are never logged. A tool failure's text is `<code>: <message>`. Draft tools never write entities: `CreateDraft` stores a pending draft with source `mcp`; an optional client `key` makes repeats `already_pending` while a draft exists (ref `k:<sha256(key)>`), without a key every call creates a new draft (ref `r:<uuid>`). Title, key and note are trimmed (a blank title or a non-empty blank key is `invalid_input`). A user can have about 500 pending MCP drafts (a soft cap: parallel calls can overshoot it by the number in flight) (`mcptool.DefaultMaxPendingDrafts`, counted in the same transaction as the create by `drafts.Store.CreateLimited`); parallel creates with the same key conflict in badger, so `CreateLimited` retries via `storage.RetryConflicts` and the loser gets `already_pending`; beyond that `CreateDraft` returns `too_many_pending` until the user decides some. Every tool sets `readOnlyHint` and `idempotentHint` and explicit `destructiveHint: false`, `openWorldHint: false` (`Spec.Idempotent` marks repeatable write tools). `attach_paperless_documents` derives the entity URL from `PUBLIC_URL` (`public_url_not_configured` when unset; there is no request-header fallback), checks that the entity exists for the user and that its module is enabled. `DisableLocalhostProtection` is on because requests carry a bearer token and a reverse proxy on the same host would otherwise be rejected. Config: `PUBLIC_URL` (absolute http(s) URL, trailing slash trimmed, no query/fragment; empty = unset). Metrics: `mcp_tool_calls_total{tool,outcome}` (`ok|tool_error|forbidden|internal_error`) and `mcp_tool_call_duration_seconds{tool}`.

**Logging:** `log/slog` — JSON handler in production, text in dev.

**Metrics:** Prometheus via `/metrics` endpoint. Tracks `mcp_tool_calls_total` (see MCP), `http_requests_total`, `http_request_duration_seconds`, `http_active_requests`, and for the LLM client `llm_requests_total{operation,outcome}`, `llm_request_duration_seconds{operation}`, `llm_tokens_total{operation,type}`, `llm_retries_total{operation}`.

**Middleware chain (outermost first):** RequestID → Recovery → Metrics → Logging → CORS → handler. Module routes additionally pass the enablement gate after auth.

**Auth:** JWT-based authentication. Registration and login seed default data for every enabled module (idempotent; re-enabling a module in settings re-seeds it). Stores accept `userID` as a parameter; handlers extract it from auth context. Passwords must be at least 8 characters (register and change). `/auth/login` and `/auth/register` share a per-IP token-bucket rate limit (`internal/middleware/ratelimit.go`): `AUTH_RATE_LIMIT` requests (default 10) per `AUTH_RATE_WINDOW` (default `1m`), 0 disables; set `TRUST_PROXY=true` behind a reverse proxy so client IPs come from `X-Real-IP`/`X-Forwarded-For`.

**Personal access tokens in the API:** `middleware.Auth(secret, opts...)` accepts a JWT or a personal access token (`kpat_…`, `WithPATs(verifier)`); it puts a `middleware.Principal` (`UserID`, `Kind` `jwt|pat`, `TokenID`, `Scopes`) into the context (`GetPrincipal`, `IsPAT`, `HasScope`; `GetUserID` keeps working). Failures are an identical `401 {"error":"unauthorized"}` for unknown, revoked, expired and malformed tokens (a verifier error is `500`); options `PATOnly()` (reject JWTs) and `WithChallenge("Bearer")` (set `WWW-Authenticate`) are meant for `/mcp`. Tokens are never logged. Reach is an explicit table keyed by the registered mux pattern (`internal/server/scopes.go`, enforced by `middleware.ScopeGuard` around the API mux, JWT requests pass untouched, a pattern missing from the table is denied): `read` for every `GET` (including the exports), `drafts` for `PUT /drafts/{id}` and the draft accept/reject, `links` for `POST /paperless/links/{entityType}/{entityId}` and `POST /ledger/transactions/{id}/references`, `denied` (never reachable with a token) for every other mutation, `jwt-only` for `/tokens*`, `PUT /settings/password` and `GET /ledger/bank/aspsps` (the bank list spends Enable Banking quota; the other bank mutations, including sync, are `denied`, `GET /ledger/bank/connections` is `read`; the public callback has no entry) (`/auth/*` is public and outside the API mux). A rejected request gets `403 {"error":"insufficient scope","code":"insufficient_scope"}`; 404/405 are answered by the mux as usual and module gating still applies afterwards. A new route must get a table entry: `TestRouteRulesCoverRoutes` builds the real app (`buildApp`) and fails for missing or stale entries. **Accepted residual risk (decided with the user, not changed):** over the REST API the scopes are broader than the MCP tools. A `drafts` token can accept drafts, including with an unverified `entityId` (accept does not check that the entity exists), so an agent can clear its own drafts from the inbox without the user reviewing them; for **paperless-sourced** drafts, accepting also stores a paperless link for the unchecked entity, writes the request's `entityUrl` into the document's "Kontor" custom field and swaps the inbox tag for the done tag in paperless, and rejecting removes the inbox tag; `PUT /drafts/{id}` can edit the input of any pending draft; and a `links` token chooses the `entityUrl` that is written into the user's paperless "Kontor" custom field and skips the entity-exists check of `POST /paperless/links/{entityType}/{entityId}`. The MCP tools do not have these gaps: `attach_paperless_documents` derives the URL from `PUBLIC_URL` and verifies the entity, and there is no MCP tool to accept drafts. Give tokens only the scopes a client needs, and REST access only to clients you trust with these.

- `DELETE /api/v1/paperless/links/{entityType}/{entityId}/{documentId}` — Detach a document; clears the back-link custom field only if it still points at this entity, and removes the done tag when no other entity links the document
- `GET /api/v1/paperless/pipeline` — Draft pipeline settings (`{enabled, inboxTag, doneTag}`; defaults `false`, `kontor-inbox`, `kontor`)
- `PUT /api/v1/paperless/pipeline` — Save pipeline settings (tags non-empty, at most 128 characters, distinct case-insensitively)
- `POST /api/v1/paperless/pipeline/run` — Run a pipeline pass for the current user now (`{found, created, skipped, failed}`; 409 when the LLM is off, paperless is not configured, the pipeline is disabled, no target module is enabled or a pass is already running; 502 on paperless errors)
- `GET /api/v1/drafts?status=` — List drafts, newest first (`pending` by default; `accepted`, `rejected`, `all`)
- `GET /api/v1/drafts/summary` — `{pending, total}` draft counts
- `GET /api/v1/drafts/{id}` — Get a draft
- `PUT /api/v1/drafts/{id}` — Edit a pending draft (`{targetType, parentId, input}`; 400 for an unknown type or a parent on a type without parents; 409 when decided)
- `POST /api/v1/drafts/{id}/accept` — Accept a pending draft after the frontend created the entity (`{entityType, entityId, entityUrl}`; `entityType` must match `targetType`); runs the source hook (paperless: link, back-link, tag swap; ledger: link the group's payments to the contract) and returns `{draft, warnings}`; 409 when decided
- `POST /api/v1/drafts/{id}/reject` — Reject a pending draft; runs the source hook (paperless: remove inbox tag; ledger: remember the rejected group) and returns `{draft, warnings}`; 409 when decided
- `POST /api/v1/quick-add` — Classify a typed note (`{text, targetType?}`, at most 2000 characters; `targetType` forces `purchase|contract|cost`) or, as `multipart/form-data`, a PDF or image (`file` at most 10 MiB, optional `text` hint and `targetType`; 413 `file_too_large`, 415 `unsupported_file`, 409 `vision_not_configured` for an image without `LLM_VISION_MODEL`, 422 `pdf_no_text` / `file_unreadable`) into `{targetType, parentId, input, confident, note, currency?}` (`currency{code, amount, converted, rate?, rateDate?}` for non-EUR amounts); nothing is stored. 409 when the LLM is off or no target module is enabled, 400 for empty/too long text or an invalid/disabled `targetType`, 504 on LLM timeout, 502 on other transient LLM errors; non-retryable LLM errors return `targetType: none` with a note
- `POST /mcp` — MCP endpoint for agents (personal access token only; `initialize`, `tools/list`, `tools/call`; 401 + `WWW-Authenticate: Bearer` otherwise)
- `GET /healthz` — Liveness probe
- `GET /readyz` — Readiness probe (checks DB)
- `GET /metrics` — Prometheus metrics

Linked internal transfers are intentionally protected from normal category assignment until the user explicitly unlinks them.
